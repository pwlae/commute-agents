Commute Agents: the whole guide

Every lesson on one page, for printing.

Lesson 0 · Start here · 1 question

How this course works

This course is for engineers who build real products and want AI agents to do far more of the work. One lesson fits one commute: about 10 minutes of reading, then a few quick questions.

The idea

Most teams use agents like a faster keyboard. The agent writes code that looks hand-written, and a person reviews every line as if a colleague wrote it. Writing got 10 times faster. Reviewing didn't. So the whole team gets maybe 2–3 times faster, not 10.

The fix is not a better prompt. It is moving the checks a reviewer does before the pull request, into things a machine can run: tests, lint rules, contract checks, an agent that reviews its own work. Then people review the rules, not every diff.

You don't need to be on an "AI team" to build this. You know your product, your services and your team's unwritten rules. That is exactly the knowledge an agent is missing. The course goes in four parts:

Part 1 needs only your phone. Parts 2 and 3 have a short hands-on step for when you are at a laptop. Part 3 uses a practice system with several services, Kafka, a saga and real database migrations, because agents find distributed systems much harder than a one-page website, and that is where most of us work.

How each lesson works

  1. Read the idea. Short, plain words, one picture.
  2. Answer the Predict cards. Each one is a small situation from work. Guess first, then tap Show answer. If you were right, tick I got it.
  3. Use it at work. What to do differently tomorrow, and what to say if a colleague asks.

Don't spend more than two minutes on a card. A wrong guess you then read about teaches you more than a long think.

Your turn

Question 1 · ~2 min

An agent writes a pull request in 10 minutes. A colleague then spends 50 minutes reviewing it line by line and asks for three changes. Which step should you speed up first?

Show answer

The review. It is five times longer than the writing. Speeding up the agent further barely changes the total. The big gain comes from catching those three problems before the PR: if a test or a lint rule had flagged them, the agent would have fixed them itself, and the human would only check what a machine can't.

  • Next time you or a colleague opens an agent-written PR, write down two numbers: minutes spent writing and minutes spent reviewing.
  • Pick one review comment from that PR that a machine could have caught. Keep it. In Part 2 you will turn comments like that into checks.

Interesting fact: Amdahl's law

In 1967 the computer architect Gene Amdahl pointed out that speeding up one part of a job can only help as much as that part's share of the whole. Make one part infinitely fast, and the time for the other parts is still there. He was talking about parallel processors, but it applies to teams too. If writing code is 30% of the time from ticket to production, then even instant code makes delivery at most about 1.4 times faster (1 ÷ 0.7). To go further, you have to speed up the rest: review, testing, deployment.

  • Agents made writing fast. Line-by-line review is now the bottleneck.
  • The way out: move review checks before the PR, into things a machine runs.

Lesson 1 · Part 1 · The model · 5 questions

Tokens and the context window

Read first: How this course works

A model never sees your text as letters or words. It sees tokens: small pieces of text, each turned into a number. Prices, limits and the size of the model's working memory are all counted in tokens, so knowing what makes text "expensive" tells you where an agent's money and memory go.

The idea

Think of how you read a familiar word: you don't spell it out, you see it whole. A rare surname you read in chunks. A model does something similar, but more strictly. Before it reads anything, a program called the tokenizer cuts the text into pieces from a fixed vocabulary of tens of thousands to a few hundred thousand pieces. Common words are one piece. Rare words, names and IDs are cut into many small pieces.

  1. Split. The tokenizer cuts the text into known pieces. Each piece is a token.
  2. Number. Each token becomes a number, its position in the vocabulary. The model only ever sees these numbers.
  3. Read, then write. The model reads all the tokens you send (input tokens), then writes its reply one token at a time (output tokens).
  4. Fit. Everything has to fit in the context window: the most tokens the model can handle in one request, counting both what you send and what it writes back.

Two English words cost one token each. The 8-character ID costs 9 (with the space). That is the whole lesson in one line: familiar text is cheap, random text is expensive.

Up close

How big is a token? OpenAI's rule of thumb for English is about 4 characters, or ¾ of a word, per token: 100 tokens ≈ 75 words. Tokenizers differ, though. Anthropic says a token was about 3.5 English characters on its older models, and that Claude Opus 4.7 and later use a new tokenizer that makes about 30% more tokens from the same text. So a rule of thumb is a rough guess. For a real number, count with the model you will use.

Why everything is priced in tokens. The model's work grows with the number of tokens it reads and writes, not with characters or requests. So the API bills input and output tokens separately, and output costs more. On Anthropic's price list, output tokens cost 5 times as much as input tokens on every current model (for example, Claude Sonnet 5.5 is $2 per million input tokens and $10 per million output tokens). Why writing costs more is the subject of Reading fast, writing slow.

The context window is the model's whole working memory. The model remembers nothing between requests. What it "knows" in a session is exactly what is in the window: the tool list, the system prompt, your context files, every message, every tool result, and the reply it is writing. Recent Claude models have a 1-million-token window. If what you send is already bigger than the window, the API refuses the request with a "prompt is too long" error. It does not quietly drop old messages for you; the harness (the program running the agent) has to make room.

Counting tokens with the API. Anthropic has a free endpoint that counts the input tokens of a request without running it. It takes the same fields as a normal request. The answer is an estimate, but a close one:

import anthropic

client = anthropic.Anthropic()
path = "orders/service.py"
text = open(path).read()

r = client.messages.count_tokens(
    # count with the model you use:
    # tokenizers differ
    model=MODEL,
    messages=[{
        "role": "user",
        "content": text,
    }],
)
print(path, r.input_tokens)

Other providers have their own counters. OpenAI publishes its tokenizers as an open-source library, tiktoken, so you can count offline.

Worked example

Here is some typical text, counted with OpenAI's open o200k_base tokenizer. Other tokenizers give different numbers, but the pattern is the same:

TextCharsTokensChars per token
English sentence about retries98204.9
Python retry function163394.2
One JSON log line with IDs2261161.9
A UUID36361.0

Ordinary code is nearly as cheap as English: return, except and four-space indents are all common pieces. Timestamps, trace IDs and UUIDs are not, so they fall apart into single characters. A log line costs more than twice as much per character as prose.

Language matters too. "The quick brown fox jumps over the lazy dog." is 10 tokens. The same sentence in Russian is 20, and in Japanese 20, even though the Japanese has fewer than half the characters. A NeurIPS 2023 study by Petrov and colleagues found that the same text translated into different languages can need up to 15 times more tokens. Those languages pay more per message and fill the window faster.

Question 1 · ~2 min

A model that writes working Kafka consumers tells you "strawberry" has two r's. How can it be good at code and bad at this?

Show answer

It never sees the letters. In "How many r's in strawberry?", the word " strawberry" (with its leading space) is a single token in OpenAI's o200k_base tokenizer, for example: one number. To get it right, ask it to spell the word out one letter per line first, or to run a line of code. Then each letter is its own token.

Question 2 · ~2 min

You give your agent a 200 KB JSON log from a failing service. Using "4 characters per token", you expect about 50,000 tokens. The session's token count jumps by about 100,000. Why?

Show answer

Logs are full of strings that aren't in the tokenizer's vocabulary. Timestamps, trace IDs, span IDs and UUIDs split into one or two characters per token, and the quotes and braces around each field add more. A JSON log can easily be 2 characters per token, not 4. Filter before the agent reads it: grep the error lines, or jq the few fields that matter.

Question 3 · ~2 min

To change 3 lines in an 800-line file, your agent writes the whole file out again instead of making a small edit. What does that cost you?

Show answer

Thousands of output tokens instead of a few dozen. Output is the expensive kind (5 times the input price on Anthropic's list), and it is written one token at a time, so it is slow too. A small edit costs almost nothing. Prefer tools and prompts that produce edits or diffs, not whole files.

Question 4 · ~3 min

A long agent session keeps growing: files, test runs, logs. It finally gets bigger than the model's context window. What happens next?

Show answer

The API refuses the request with a "prompt is too long" error. It doesn't forget old messages on its own. The harness must make room first. Coding agents do this by compaction: summarising older parts of the conversation when it gets close to the limit. The summary is shorter than what it replaces, so details from early on can be lost. That is one reason a fresh session for a new task often works better.

Use it at work

  • Estimate the token size of the files your agent reads in every session: the context file (such as CLAUDE.md or AGENTS.md), the main service files, a typical log. Characters ÷ 4 is a quick guess for prose; use a token counter for code and logs.
  • In your coding agent, look at what fills the window. In Claude Code, /context shows what is using the window. The biggest users are usually tool results: long test output, whole-file reads and raw logs.
  • Cut those before they reach the agent: filter logs to the error lines, run tests so they print failures only, and ask for edits, not whole files.

If someone asks "why did this cost so much when I only typed one line?": "The model bills by tokens, and every step sends everything it has read so far, including every log and file. Logs full of IDs cost about twice as many tokens per character as normal text, so trimming what goes in is the cheapest fix."

Interesting fact: The word GPT couldn't say

In January 2023, Jessica Rumbelow and Matthew Watkins were studying GPT-3's vocabulary of 50,257 tokens and found a cluster of strange ones, such as " SolidGoldMagikarp", " petertodd" and "StreamerBot". When asked to simply repeat " SolidGoldMagikarp", the models replied "distribute". Other tokens got answers like "I can't hear you" or outright insults. Their best explanation: the vocabulary was built from scraped web text that probably included Reddit threads, shop back-ends and game logs, but the models were trained on cleaner text. So these tokens existed, yet the models had almost never seen them used, and didn't know what to do with them. About a week after their post, ChatGPT appeared to have been patched, and "glitch tokens" became a research topic of their own.

Facts checked: November 2026 (Anthropic API docs: token counting, context windows, pricing; Claude Code docs; OpenAI's token guide; Petrov et al., NeurIPS 2023; Rumbelow and Watkins, 2023).

  • Count with the real model's tokenizer, and keep big tool results out of the window.

Lesson 2 · Part 1 · The model · 5 questions

How the next token is chosen

Read first: Tokens and the context window

A model doesn't pick the next word. It gives a probability to every token it knows, and then a dice roll picks one. That roll is why the same prompt gives a different answer, and the same ticket a different diff, every time you run it.

The idea

Think of the word suggestions above your phone keyboard. It offers three words, ranked. Now imagine that instead of always taking the first one, you roll a weighted die: the top word wins most often, but sometimes the second or third one does. Do that for every word of a message and you get a slightly different message each time.

A language model writes exactly like that, one token at a time:

  1. Score. The model reads everything in the context and gives a score to every token in its vocabulary, all of them, not just a few good ones. These raw scores are called logits.
  2. Turn scores into probabilities. A function called softmax turns the scores into probabilities that add up to 100%. A higher score means a higher chance.
  3. Pick. A small program called the sampler picks one token at random, weighted by those probabilities. This is sampling.
  4. Repeat. The picked token is added to the context, and the model scores the next position, now taking that token into account.

The key thing is step 4. Each pick changes everything after it. If the third token of a plan is "retry" in one run and "timeout" in another, the two runs are now answering slightly different questions, and they drift further apart with every token. In an agent, the drift is bigger still: a different first step means different files read, different tool results, and a different diff at the end.

Up close

Two settings change how the die is weighted. Both act on the probabilities before the pick:

  • Temperature sharpens or flattens the probabilities. Below 1, likely tokens get more likely and unlikely ones fade away. Above 1, the field evens out and rare tokens get a real chance. At 0, the sampler just takes the top token every time. That is called greedy decoding.
  • Top-p (also called nucleus sampling) drops the long tail. It keeps the smallest group of top tokens whose probabilities add up to p, say 0.9, and throws the rest away. The model's vocabulary has tens of thousands of tokens, and most of them are nonsense in any given spot. Top-p, introduced in a 2019 paper by Ari Holtzman and colleagues, makes sure none of that nonsense can win the roll.

Some APIs also have top-k: keep only the k most likely tokens. Here is the whole sampler in a few lines of Python:

import math
import random

def sample(scores, t=1.0, top_p=1.0):
    # scores: {token: logit}
    if t == 0:  # greedy
        return max(scores,
                   key=scores.get)
    m = max(scores.values())
    w = {k: math.exp((v - m) / t)
         for k, v in scores.items()}
    total = sum(w.values())
    probs = sorted(
        ((p / total, k)
         for k, p in w.items()),
        reverse=True)
    # top-p: keep the head only
    keep, acc = [], 0.0
    for p, k in probs:
        keep.append((p, k))
        acc += p
        if acc >= top_p:
            break
    ps, ks = zip(*keep)
    return random.choices(
        ks, weights=ps)[0]

Dividing the scores by t is the whole trick. A small t stretches the gaps between scores, so the leader pulls away. A large t squeezes them together.

Many newer APIs won't let you set these at all. On Anthropic's API, Claude Opus 4.7 and later models return a 400 error if you send temperature, top_p or top_k; the docs say to remove them and steer the model with the prompt instead. OpenAI's reasoning models have the same rule: when reasoning is on, remove temperature and top_p. The vendors don't publish their full reasons. What you control instead is the prompt and the effort level (see Thinking and effort levels). Open-weight models that you run yourself still give you every knob.

Worked example

An agent has written "The fix is to add a" and is choosing the next token. Say the model's probabilities are: retry 50%, timeout 30%, lock 12%, cache 5%, and the last 3% spread thinly over 3,000 unlikely tokens. Here is what each setting does to the odds:

Tokent=1t=0.5t=1.5top-p 0.9
retry50%70%22%54%
timeout30%25%16%33%
lock12%4%9%13%
cache5%1%5%0%
3,000 others3%~0%49%0%

Low temperature makes the favourite stronger. High temperature is the surprise: each junk token is still unlikely, but there are 3,000 of them, so together they now win about half the time. That is why a "creative" temperature quickly turns into made-up words. Top-p 0.9 keeps retry, timeout and lock (92% together), drops everything else, and scales the three back up to 100%.

Question 1 · ~2 min

You give an agent the same ticket twice, in two fresh sessions, with the same repo and the same prompt. You get two different diffs. One passes the tests; the other fails one. Is something broken?

Show answer

No. That is sampling. Every token is a weighted random pick, and an early difference (a different file read first, a different plan) grows into a different diff. Each run is one draw from many possible results. So judge an agent setup by how often it succeeds over several runs, and let the tests decide which diff is correct, not how the code looks.

Question 4 · ~3 min

You run an open-weight model on your own server with temperature 0. Alone on your laptop, the same prompt gives the same answer every time. In production, with many users, the same prompt sometimes gives a different answer. How, if there's no randomness?

Hint
What else is the server doing while it runs your request?
Show answer

Your request is batched with other people's. Servers run many requests together on the GPU, and how many depends on the load at that moment. With a different batch size, the GPU adds up the same numbers in a different order, and floating-point sums can round differently. A tiny change in a score can flip which token is top, and then the texts drift apart. In 2025, Thinking Machines Lab ran one prompt 1,000 times at temperature 0 and got 80 different completions. They were the same for the first 102 tokens, then split at token 103. With special "batch-invariant" GPU code, all 1,000 matched, but it ran noticeably slower.

Question 5 · ~3 min

Stretch: you add a feature that asks a model to summarise a support ticket as JSON. Your test saves one good output and asserts that every new output matches it exactly. The test is flaky. What should it check instead?

Show answer

Properties, not exact text. Check what must always be true: the output parses as JSON, matches the schema, has the right ticket ID, stays under a length limit, and mentions the product named in the ticket. For quality, run a small set of examples several times and require a pass rate, such as 9 out of 10. Exact-match tests fight sampling, and sampling wins.

Use it at work

  • Never judge an agent setup, a prompt change or a new model on one run. Run the same task at least twice, ideally a few times, before you decide anything.
  • When an agent fails a task once, rerun it before rewriting your instructions. If it fails the same way twice, the problem is likely in the setup, not in the roll of the dice.
  • Search your team's code for temperature, top_p and top_k in model calls. On newer models they cause errors; remove them before an upgrade and test with property checks, not exact strings.

If someone asks "why does the AI give a different answer every time?": "The model gives a probability to every possible next word and then picks one at random, weighted by those probabilities, for every word it writes. So each run is one sample, and the way to judge it is to run it a few times and count how often the result is right."

Interesting fact: Why it's called temperature

The word comes from 19th-century physics. Ludwig Boltzmann described how the particles of a gas share out energy: at temperature T, a state with energy E has a probability proportional to e−E/kT. Cold, almost everything sits in the lowest-energy state. Hot, all states become nearly equally likely. Softmax with a temperature is the same formula, with a token's score in place of minus its energy. In 1983, Scott Kirkpatrick and colleagues at IBM borrowed it to design computers: their "simulated annealing" placed and wired chips by starting "hot" and cooling slowly, like metal being annealed. In 1985, Geoffrey Hinton, David Ackley and Terrence Sejnowski built the "Boltzmann machine", a neural network named after Boltzmann. In 2024 Hinton shared the Nobel Prize in Physics with John Hopfield, and the Nobel committee pointed to the Boltzmann machine's use of statistical physics.

Facts checked: November 2026 (Anthropic and OpenAI API docs; Holtzman et al., ICLR 2020; Thinking Machines Lab, 2025; Kirkpatrick et al., Science, 1983; Nobel Prize in Physics 2024).

  • Temperature sharpens or flattens the odds; top-p cuts off the long tail of junk tokens. Newer APIs often don't let you set either.
  • Even temperature 0 isn't fully repeatable on a busy server. Judge agents over several runs, never one.

Lesson 3 · Part 1 · The model · 5 questions

Reading fast, writing slow

Read first: Tokens and the context window

A model reads your whole prompt at once, but writes its answer one token at a time. That one fact explains why a huge prompt can still get a quick reply, why long answers are slow, and why output tokens cost more than input tokens.

The idea

Picture a cook in a huge kitchen. To make anything, they must walk past every shelf in the pantry. Walking is slow; cooking is quick. For a banquet where every dish is already known, one walk is enough: they grab what all the dishes need and cook them side by side. But for a tasting menu where each course depends on how the last one turned out, they must walk the whole pantry again for every course.

A model on a GPU is that cook. The pantry is the model's weights, its billions of learned numbers, stored in GPU memory. Every step of work has to read all of them. Reading them takes far longer than the maths done with them. So a request has two phases:

  1. Prefill (reading). The model takes in all the prompt tokens at the same time. One pass over the weights serves thousands of tokens, so the GPU is kept busy and the work goes fast.
  2. Decode (writing). The model writes one token, adds it to the text, and only then can it write the next, because each token depends on the ones before it. Every new token needs another full pass over the weights.
  3. Remember as you go. While reading, the model saves notes about every token it has seen, so writing the next token doesn't mean re-reading the whole text. These notes are the KV cache.

The rule to remember: input tokens are read together, output tokens are written in a queue.

Up close

Why writing is slow. Google's researchers put the bottleneck plainly: GPUs and TPUs can do hundreds of trillions of operations per second, but can move only trillions of bytes per second from memory, about a hundred times less. Writing one token does only a few operations per byte of weights read, so the chip spends most of its time waiting for memory. NVIDIA describes prefill as "highly parallelized" work that "saturates" the GPU, and decode as work that leaves it underused.

The KV cache in plain words. For each token, at each layer of the model, the model computes a "key" (what this token is about, for others to search) and a "value" (what it has to offer when found). Every new token looks up the keys and values of all the tokens before it. Keeping them in GPU memory means each new token only computes its own. The cache is big: NVIDIA's example, a small 7-billion-parameter model with 4,096 tokens of context, needs about 2 GB of KV cache for one request. This cache is exactly what prompt caching saves between requests.

Two numbers for speed. Time to first token (TTFT) is how long you wait before the reply starts: mostly prefill, plus any time in a queue. Output tokens per second is the decode speed. Total time is roughly TTFT plus output tokens divided by that speed. You can measure both with streaming:

import time

t0 = time.monotonic()
first = None
with client.messages.stream(
    model=MODEL,
    max_tokens=2000,
    messages=history,
) as s:
    for text in s.text_stream:
        if first is None:
            first = time.monotonic()
    msg = s.get_final_message()
end = time.monotonic()

n = msg.usage.output_tokens
print("TTFT s:", first - t0)
print("tok/s:", n / (end - first))

Providers sell the two separately. Anthropic's fast mode, for example, gives up to 2.5 times more output tokens per second on Claude Opus 5.5 for twice the price, and the docs say the gain is in output speed, not time to first token.

Why output costs more. On Anthropic's price list, output tokens cost 5 times as much as input tokens on every current model. Providers don't publish their costs, but the mechanism points the same way: a pass over the weights during prefill produces thousands of tokens; during decode it produces one per request. Providers batch many users' requests into each decode pass to share the cost, but every request in the batch needs its own KV cache in GPU memory, which limits how many fit.

Worked example

Round numbers for illustration (real speeds depend on the model, the provider and the load): the model reads 20,000 tokens a second and writes 50 a second.

RequestReadingWritingTotal
100k prompt, 50-token answer5 s1 s~6 s
5k prompt, 5k answer0.25 s100 s~100 s
Agent rewrites a 6k-token file—120 s~2 min
Agent edits 10 lines (200 tokens)—4 s~4 s

The request with 20 times more input finishes about 16 times sooner. In an agent, every tool call is output too: the arguments of a "write file" call are the whole file, decoded token by token. So is thinking, which is billed and written as output (see Thinking and effort levels).

Request A sends a 100,000-token prompt (a big chunk of a repo) and gets a 50-token answer. Request B sends 5,000 tokens and gets a 5,000-token answer. Which one finishes first?

Show answer

Question 2 · ~2 min

A colleague asks why Anthropic charges 5 times more for an output token than an input token. "A token is a token." What do you say?

Show answer

They are different work for the GPU. Input tokens are read together: one pass over the model's weights handles thousands of them. Output tokens are written one at a time, and each one needs its own pass. Batching many users together helps, but each user's KV cache takes GPU memory, so a GPU makes far fewer output tokens per hour than it reads input tokens. Providers don't publish their costs, but that is why the direction makes sense.

Use it at work

  • When speed matters, ask for short outputs: an edit or a diff, not the whole file; a verdict, not an essay. Check that your agent uses its edit tool for small changes.
  • When a step feels slow, tell the two phases apart: a long wait before text appears is reading (shrink or cache the input); slow streaming is writing (ask for less output, or use a faster model).
  • Split long, independent writing jobs across parallel agents instead of one long answer.

If someone asks "why is the agent so slow when the model is so fast?": "Models read the whole prompt at once but write one token at a time, so it's the length of the answer that costs time. Asking for diffs instead of whole files often makes it several times faster."

Interesting fact: Guess first, check in one go

In November 2022, Yaniv Leviathan, Matan Kalman and Yossi Matias at Google published "Fast Inference from Transformers via Speculative Decoding" (ICML 2023). The idea borrows from CPUs, which guess which way a branch will go and do the work early. A small, fast model drafts the next few tokens. The big model then checks all of them in one pass, the way it reads a prompt, keeps the drafted tokens it agrees with up to the first one it rejects, and writes that one itself. Many tokens are easy (copying a name from earlier in the text), so the draft is often right. Their 11-billion-parameter T5 model, helped by a 60-million-parameter one, ran 2 to 3 times faster, with exactly the same outputs as before. DeepMind published the same idea independently in February 2023, speeding up its 70-billion-parameter Chinchilla by 2 to 2.5 times. Google says it now uses the technique in AI Overviews in Search.

Facts checked: November 2026 (Anthropic API docs: pricing, fast mode, reducing latency; NVIDIA's LLM inference optimisation guide; Leviathan et al., ICML 2023; Chen et al., DeepMind, 2023; Google Research blog, 2024).

Remember

  • Prefill reads the whole prompt in parallel; decode writes one token at a time, each needing a full pass over the weights.
  • Time to first token is mostly reading; output tokens per second is writing. Long answers, not long prompts, make requests slow.
  • Output costs more because it uses the GPU far less efficiently. Ask agents for diffs and verdicts, not whole files and essays.

Prompt caching

Read first: Tokens and the context window, Reading fast, writing slow

Every time an agent takes a step, it sends the whole conversation to the model again. Prompt caching lets the provider reuse the work it already did on the unchanged start of that conversation, which makes long agent sessions several times cheaper and faster.

The idea

Picture a book club with a strange rule: before each meeting you must re-read the book from page one, then read the new chapter. That gets slow by chapter 20. So you keep notes on everything you've already read, and only read the new chapter properly.

There is a catch. If someone changes a sentence on page 3, your notes from page 3 onwards are useless, because everything after it might read differently now. You keep only the notes up to the first change.

A model API works like that book club:

  1. The API remembers nothing between requests. Each request sends everything: the tool list, the system prompt (the instructions at the start), and every message so far. Step 40 of an agent session sends steps 1–39 again.
  2. Reading the prompt is real work. For every token, the model computes internal data it needs to write the answer (the "KV cache", explained in Reading fast, writing slow).
  3. The provider can keep that data for a few minutes. If your next request starts with exactly the same bytes, it reuses the saved work up to the first byte that differs. That is a prefix match: only the unchanged start counts.

The order matters: tools first, then the system prompt, then messages. A change near the top throws away everything below it. A new message at the bottom throws away nothing. That is the normal, cheap case.

Up close

Here is a request with caching on, using Anthropic's Python SDK. The usage fields tell you what happened:

resp = client.messages.create(
    model=MODEL,
    max_tokens=2000,
    # cache everything up to the
    # last block, moving each turn
    cache_control={
        "type": "ephemeral"
    },
    system=SYSTEM_PROMPT,
    messages=history,
)
u = resp.usage
# saved to the cache this time
print(u.cache_creation_input_tokens)
# reused from the cache
print(u.cache_read_input_tokens)
# read at full price
print(u.input_tokens)

On Anthropic's API (other providers differ in the details):

  • Reading from the cache costs about a tenth of the normal input price, and even less on some newer models.
  • Writing to the cache costs a bit more than normal: 1.25 times for the default 5-minute lifetime, 2 times for a 1-hour lifetime. Every cache read resets the timer.
  • Short prompts aren't cached. Below a minimum length (512 to 4,096 tokens, depending on the model) nothing is saved, and there is no error. You just see cache_read_input_tokens stay at 0.

Other providers cache too, some fully automatically, and open-source model servers do the same thing (often called "prefix caching"). The prefix rule is the same everywhere, because it comes from how models read text.

What breaks the cache

ChangeWhat must be re-read
New message at the endOnly the new message
Timestamp in the system promptSystem prompt and all messages
Tool added, removed or reorderedEverything
Switch to another modelEverything (each model has its own cache)
Edit an old messageThat message and all after it
Pause longer than the lifetimeEverything

Watch for invisible changes too: JSON with keys in a random order, or a request ID in the prompt. The text means the same, but the bytes differ.

Worked example

One step of an agent session sends 100,000 tokens. 97,500 of them are the same as the previous step, and 2,500 are new (the last tool result and the reply). Count cost in "full-price tokens":

Without cacheWith cache
97,500 old tokens97,500× 0.1 = 9,750
2,500 new tokens2,500× 1.25 = 3,125
Total100,00012,875

About 8 times cheaper per step, and the reply starts sooner, because the model skips re-reading. Over a 40-step session, that is the difference between a tool your company can afford and one it can't.

Question 3 · ~2 min

You leave a long agent session for 15 minutes to get coffee, then type "continue". The first reply is slow and costs more than usual. The next ones are fast again. Why?

Show answer

The cache expired. The default lifetime is 5 minutes, and nothing used the cache while you were away. The first request re-read the whole conversation at full price and saved it again. The ones after that hit the new cache. A 1-hour lifetime avoids this, at a higher price for writing.

Question 4 · ~3 min

To save money, you switch a long session from the big model to a small one for "easy" steps, then switch back. The bill goes up instead of down. Why?

Show answer

Each model has its own cache. Every switch means the other model reads the whole conversation at full price. That can cost more than the cheaper model saves. A better way: give the easy job to a separate helper agent (a subagent) with its own short context, and keep the main session on one model.

Question 5 · ~3 min

Stretch: your harness shortens long tool outputs from 30 steps ago, a little on every step, to keep the context small. Why can this cost more than doing nothing?

Hint
Where in the prompt is the edit, and what comes after it?
Show answer

Each edit sits in the middle of the conversation, so everything after it is re-read at full price on every step. You save some tokens but lose the cache for most of the conversation. If you must shrink the context, do it rarely and all at once, then let the cache build up again. That is how "compaction" (summarising the conversation) is designed to work.

Use it at work

  • If your team calls an LLM API, log cache_read_input_tokens (or your provider's version of it). If it stays at 0 across similar calls, look for something that changes at the start: a date, a user name, a request ID, unsorted JSON.
  • Move anything that changes per request to the end of the prompt. Keep the system prompt and tool list frozen.
  • In your coding agent, don't keep switching models or turning tools on and off in one long session. Start a fresh session instead.

If someone asks "why is our LLM bill so high?": "Check the cache hit rate first. Every agent step sends the whole conversation again, so if something at the start changes every time, we pay full price for the entire history on every step."

Interesting fact: A cache built like an operating system

In 2023, researchers at UC Berkeley released vLLM, an open-source server for running language models. Its key idea, PagedAttention, borrows a trick from operating systems: instead of keeping each request's KV cache in one large block of GPU memory, it splits it into small fixed-size pages, like virtual memory. Their paper reported 2–4 times higher throughput than the best systems of the time. The same pages made prefix caching cheap: vLLM identifies each page by a hash of its tokens and all the tokens before it, so two requests that start the same way simply share pages.

Facts checked: November 2026 (Anthropic API docs; vLLM paper and docs).

Remember

  • Every agent step sends everything again. Caching reuses the unchanged start.
  • Order: tools → system prompt → messages. A change anywhere loses everything after it.
  • Keep the start frozen: no timestamps, fixed tools, one model per session. Watch the cache-read numbers.
