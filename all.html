Lesson 0 · Start here · 1 question

How this course works

This course is for engineers who build real products and want AI agents to do far more of the work. One lesson fits one commute: about 10 minutes of reading, then a few quick questions.

The idea

Most teams use agents like a faster keyboard. The agent writes code that looks hand-written, and a person reviews every line as if a colleague wrote it. Writing got 10 times faster. Reviewing didn't. So the whole team gets maybe 2–3 times faster, not 10.

The fix is not a better prompt. It is moving the checks a reviewer does before the pull request, into things a machine can run: tests, lint rules, contract checks, an agent that reviews its own work. Then people review the rules, not every diff.

You don't need to be on an "AI team" to build this. You know your product, your services and your team's unwritten rules. That is exactly the knowledge an agent is missing. The course goes in four parts:

Part 1 needs only your phone. Parts 2 and 3 have a short hands-on step for when you are at a laptop. Part 3 uses a practice system with several services, Kafka, a saga and real database migrations, because agents find distributed systems much harder than a one-page website, and that is where most of us work.

How each lesson works

  1. Read the idea. Short, plain words, one picture.
  2. Answer the Predict cards. Each one is a small situation from work. Guess first, then tap Show answer. If you were right, tick I got it.
  3. Use it at work. What to do differently tomorrow, and what to say if a colleague asks.

Don't spend more than two minutes on a card. A wrong guess you then read about teaches you more than a long think.

Interesting fact: Amdahl's law

In 1967 the computer architect Gene Amdahl pointed out that speeding up one part of a job can only help as much as that part's share of the whole. Make one part infinitely fast, and the time for the other parts is still there. He was talking about parallel processors, but it applies to teams too. If writing code is 30% of the time from ticket to production, then even instant code makes delivery at most about 1.4 times faster (1 ÷ 0.7). To go further, you have to speed up the rest: review, testing, deployment.

Lesson 1 · Part 1 · The model · 5 questions

Tokens and the context window

Read first: How this course works

A model never sees your text as letters or words. It sees tokens: small pieces of text, each turned into a number. Prices, limits and the size of the model's working memory are all counted in tokens, so knowing what makes text "expensive" tells you where an agent's money and memory go.

The idea

Think of how you read a familiar word: you don't spell it out, you see it whole. A rare surname you read in chunks. A model does something similar, but more strictly. Before it reads anything, a program called the tokenizer cuts the text into pieces from a fixed vocabulary of tens of thousands to a few hundred thousand pieces. Common words are one piece. Rare words, names and IDs are cut into many small pieces.

  1. Split. The tokenizer cuts the text into known pieces. Each piece is a token.
  2. Number. Each token becomes a number, its position in the vocabulary. The model only ever sees these numbers.
  3. Read, then write. The model reads all the tokens you send (input tokens), then writes its reply one token at a time (output tokens).
  4. Fit. Everything has to fit in the context window: the most tokens the model can handle in one request, counting both what you send and what it writes back.

Two English words cost one token each. The 8-character ID costs 9 (with the space). That is the whole lesson in one line: familiar text is cheap, random text is expensive.

Up close

How big is a token? OpenAI's rule of thumb for English is about 4 characters, or ¾ of a word, per token: 100 tokens ≈ 75 words. Tokenizers differ, though. Anthropic says a token was about 3.5 English characters on its older models, and that Claude Opus 4.7 and later use a new tokenizer that makes about 30% more tokens from the same text. So a rule of thumb is a rough guess. For a real number, count with the model you will use.

Why everything is priced in tokens. The model's work grows with the number of tokens it reads and writes, not with characters or requests. So the API bills input and output tokens separately, and output costs more. On Anthropic's price list, output tokens cost 5 times as much as input tokens on every current model (for example, Claude Sonnet 5.5 is $2 per million input tokens and $10 per million output tokens). Why writing costs more is the subject of Reading fast, writing slow.

The context window is the model's whole working memory. The model remembers nothing between requests. What it "knows" in a session is exactly what is in the window: the tool list, the system prompt, your context files, every message, every tool result, and the reply it is writing. Recent Claude models have a 1-million-token window. If what you send is already bigger than the window, the API refuses the request with a "prompt is too long" error. It does not quietly drop old messages for you; the harness (the program running the agent) has to make room.

Counting tokens with the API. Anthropic has a free endpoint that counts the input tokens of a request without running it. It takes the same fields as a normal request. The answer is an estimate, but a close one:

import anthropic

client = anthropic.Anthropic()
path = "orders/service.py"
text = open(path).read()

r = client.messages.count_tokens(
    # count with the model you use:
    # tokenizers differ
    model=MODEL,
    messages=[{
        "role": "user",
        "content": text,
    }],
)
print(path, r.input_tokens)

Other providers have their own counters. OpenAI publishes its tokenizers as an open-source library, tiktoken, so you can count offline.

Worked example

Here is some typical text, counted with OpenAI's open o200k_base tokenizer. Other tokenizers give different numbers, but the pattern is the same:

Ordinary code is nearly as cheap as English: return, except and four-space indents are all common pieces. Timestamps, trace IDs and UUIDs are not, so they fall apart into single characters. A log line costs more than twice as much per character as prose.

Language matters too. "The quick brown fox jumps over the lazy dog." is 10 tokens. The same sentence in Russian is 20, and in Japanese 20, even though the Japanese has fewer than half the characters. A NeurIPS 2023 study by Petrov and colleagues found that the same text translated into different languages can need up to 15 times more tokens. Those languages pay more per message and fill the window faster.

Lesson 2 · Part 1 · The model · 5 questions

How the next token is chosen

Read first: Tokens and the context window

A model doesn't pick the next word. It gives a probability to every token it knows, and then a dice roll picks one. That roll is why the same prompt gives a different answer, and the same ticket a different diff, every time you run it.

The idea

Think of the word suggestions above your phone keyboard. It offers three words, ranked. Now imagine that instead of always taking the first one, you roll a weighted die: the top word wins most often, but sometimes the second or third one does. Do that for every word of a message and you get a slightly different message each time.

A language model writes exactly like that, one token at a time:

  1. Score. The model reads everything in the context and gives a score to every token in its vocabulary, all of them, not just a few good ones. These raw scores are called logits.
  2. Turn scores into probabilities. A function called softmax turns the scores into probabilities that add up to 100%. A higher score means a higher chance.
  3. Pick. A small program called the sampler picks one token at random, weighted by those probabilities. This is sampling.
  4. Repeat. The picked token is added to the context, and the model scores the next position, now taking that token into account.

The key thing is step 4. Each pick changes everything after it. If the third token of a plan is "retry" in one run and "timeout" in another, the two runs are now answering slightly different questions, and they drift further apart with every token. In an agent, the drift is bigger still: a different first step means different files read, different tool results, and a different diff at the end.

Up close

Two settings change how the die is weighted. Both act on the probabilities before the pick:

  • Temperature sharpens or flattens the probabilities. Below 1, likely tokens get more likely and unlikely ones fade away. Above 1, the field evens out and rare tokens get a real chance. At 0, the sampler just takes the top token every time. That is called greedy decoding.
  • Top-p (also called nucleus sampling) drops the long tail. It keeps the smallest group of top tokens whose probabilities add up to p, say 0.9, and throws the rest away. The model's vocabulary has tens of thousands of tokens, and most of them are nonsense in any given spot. Top-p, introduced in a 2019 paper by Ari Holtzman and colleagues, makes sure none of that nonsense can win the roll.

Some APIs also have top-k: keep only the k most likely tokens. Here is the whole sampler in a few lines of Python:

import math
import random

def sample(scores, t=1.0, top_p=1.0):
    # scores: {token: logit}
    if t == 0:  # greedy
        return max(scores,
                   key=scores.get)
    m = max(scores.values())
    w = {k: math.exp((v - m) / t)
         for k, v in scores.items()}
    total = sum(w.values())
    probs = sorted(
        ((p / total, k)
         for k, p in w.items()),
        reverse=True)
    # top-p: keep the head only
    keep, acc = [], 0.0
    for p, k in probs:
        keep.append((p, k))
        acc += p
        if acc >= top_p:
            break
    ps, ks = zip(*keep)
    return random.choices(
        ks, weights=ps)[0]

Dividing the scores by t is the whole trick. A small t stretches the gaps between scores, so the leader pulls away. A large t squeezes them together.

Many newer APIs won't let you set these at all. On Anthropic's API, Claude Opus 4.7 and later models return a 400 error if you send temperature, top_p or top_k; the docs say to remove them and steer the model with the prompt instead. OpenAI's reasoning models have the same rule: when reasoning is on, remove temperature and top_p. The vendors don't publish their full reasons. What you control instead is the prompt and the effort level (see Thinking and effort levels). Open-weight models that you run yourself still give you every knob.

Worked example

An agent has written "The fix is to add a" and is choosing the next token. Say the model's probabilities are: retry 50%, timeout 30%, lock 12%, cache 5%, and the last 3% spread thinly over 3,000 unlikely tokens. Here is what each setting does to the odds:

Tokent=1t=0.5t=1.5top-p 0.9
retry50%70%22%54%
timeout30%25%16%33%
lock12%4%9%13%
cache5%1%5%0%
3,000 others3%~0%49%0%

Low temperature makes the favourite stronger. High temperature is the surprise: each junk token is still unlikely, but there are 3,000 of them, so together they now win about half the time. That is why a "creative" temperature quickly turns into made-up words. Top-p 0.9 keeps retry, timeout and lock (92% together), drops everything else, and scales the three back up to 100%.

Question 4 · ~3 min

You run an open-weight model on your own server with temperature 0. Alone on your laptop, the same prompt gives the same answer every time. In production, with many users, the same prompt sometimes gives a different answer. How, if there's no randomness?

Hint
What else is the server doing while it runs your request?
Show answer

Your request is batched with other people's. Servers run many requests together on the GPU, and how many depends on the load at that moment. With a different batch size, the GPU adds up the same numbers in a different order, and floating-point sums can round differently. A tiny change in a score can flip which token is top, and then the texts drift apart. In 2025, Thinking Machines Lab ran one prompt 1,000 times at temperature 0 and got 80 different completions. They were the same for the first 102 tokens, then split at token 103. With special "batch-invariant" GPU code, all 1,000 matched, but it ran noticeably slower.

Interesting fact: Why it's called temperature

The word comes from 19th-century physics. Ludwig Boltzmann described how the particles of a gas share out energy: at temperature T, a state with energy E has a probability proportional to e−E/kT. Cold, almost everything sits in the lowest-energy state. Hot, all states become nearly equally likely. Softmax with a temperature is the same formula, with a token's score in place of minus its energy. In 1983, Scott Kirkpatrick and colleagues at IBM borrowed it to design computers: their "simulated annealing" placed and wired chips by starting "hot" and cooling slowly, like metal being annealed. In 1985, Geoffrey Hinton, David Ackley and Terrence Sejnowski built the "Boltzmann machine", a neural network named after Boltzmann. In 2024 Hinton shared the Nobel Prize in Physics with John Hopfield, and the Nobel committee pointed to the Boltzmann machine's use of statistical physics.

Facts checked: November 2026 (Anthropic and OpenAI API docs; Holtzman et al., ICLR 2020; Thinking Machines Lab, 2025; Kirkpatrick et al., Science, 1983; Nobel Prize in Physics 2024).

Lesson 3 · Part 1 · The model · 5 questions

Reading fast, writing slow

Read first: Tokens and the context window

A model reads your whole prompt at once, but writes its answer one token at a time. That one fact explains why a huge prompt can still get a quick reply, why long answers are slow, and why output tokens cost more than input tokens.

The idea

Picture a cook in a huge kitchen. To make anything, they must walk past every shelf in the pantry. Walking is slow; cooking is quick. For a banquet where every dish is already known, one walk is enough: they grab what all the dishes need and cook them side by side. But for a tasting menu where each course depends on how the last one turned out, they must walk the whole pantry again for every course.

A model on a GPU is that cook. The pantry is the model's weights, its billions of learned numbers, stored in GPU memory. Every step of work has to read all of them. Reading them takes far longer than the maths done with them. So a request has two phases:

  1. Prefill (reading). The model takes in all the prompt tokens at the same time. One pass over the weights serves thousands of tokens, so the GPU is kept busy and the work goes fast.
  2. Decode (writing). The model writes one token, adds it to the text, and only then can it write the next, because each token depends on the ones before it. Every new token needs another full pass over the weights.
  3. Remember as you go. While reading, the model saves notes about every token it has seen, so writing the next token doesn't mean re-reading the whole text. These notes are the KV cache.

The rule to remember: input tokens are read together, output tokens are written in a queue.

Up close

Why writing is slow. Google's researchers put the bottleneck plainly: GPUs and TPUs can do hundreds of trillions of operations per second, but can move only trillions of bytes per second from memory, about a hundred times less. Writing one token does only a few operations per byte of weights read, so the chip spends most of its time waiting for memory. NVIDIA describes prefill as "highly parallelized" work that "saturates" the GPU, and decode as work that leaves it underused.

The KV cache in plain words. For each token, at each layer of the model, the model computes a "key" (what this token is about, for others to search) and a "value" (what it has to offer when found). Every new token looks up the keys and values of all the tokens before it. Keeping them in GPU memory means each new token only computes its own. The cache is big: NVIDIA's example, a small 7-billion-parameter model with 4,096 tokens of context, needs about 2 GB of KV cache for one request. This cache is exactly what prompt caching saves between requests.

Two numbers for speed. Time to first token (TTFT) is how long you wait before the reply starts: mostly prefill, plus any time in a queue. Output tokens per second is the decode speed. Total time is roughly TTFT plus output tokens divided by that speed. You can measure both with streaming:

import time

t0 = time.monotonic()
first = None
with client.messages.stream(
    model=MODEL,
    max_tokens=2000,
    messages=history,
) as s:
    for text in s.text_stream:
        if first is None:
            first = time.monotonic()
    msg = s.get_final_message()
end = time.monotonic()

n = msg.usage.output_tokens
print("TTFT s:", first - t0)
print("tok/s:", n / (end - first))

Providers sell the two separately. Anthropic's fast mode, for example, gives up to 2.5 times more output tokens per second on Claude Opus 5.5 for twice the price, and the docs say the gain is in output speed, not time to first token.

Why output costs more. On Anthropic's price list, output tokens cost 5 times as much as input tokens on every current model. Providers don't publish their costs, but the mechanism points the same way: a pass over the weights during prefill produces thousands of tokens; during decode it produces one per request. Providers batch many users' requests into each decode pass to share the cost, but every request in the batch needs its own KV cache in GPU memory, which limits how many fit.

Prompt caching

Read first: Tokens and the context window, Reading fast, writing slow

Every time an agent takes a step, it sends the whole conversation to the model again. Prompt caching lets the provider reuse the work it already did on the unchanged start of that conversation, which makes long agent sessions several times cheaper and faster.

The idea

Picture a book club with a strange rule: before each meeting you must re-read the book from page one, then read the new chapter. That gets slow by chapter 20. So you keep notes on everything you've already read, and only read the new chapter properly.

There is a catch. If someone changes a sentence on page 3, your notes from page 3 onwards are useless, because everything after it might read differently now. You keep only the notes up to the first change.

A model API works like that book club:

  1. The API remembers nothing between requests. Each request sends everything: the tool list, the system prompt (the instructions at the start), and every message so far. Step 40 of an agent session sends steps 1–39 again.
  2. Reading the prompt is real work. For every token, the model computes internal data it needs to write the answer (the "KV cache", explained in Reading fast, writing slow).
  3. The provider can keep that data for a few minutes. If your next request starts with exactly the same bytes, it reuses the saved work up to the first byte that differs. That is a prefix match: only the unchanged start counts.

The order matters: tools first, then the system prompt, then messages. A change near the top throws away everything below it. A new message at the bottom throws away nothing. That is the normal, cheap case.

Up close

Here is a request with caching on, using Anthropic's Python SDK. The usage fields tell you what happened:

resp = client.messages.create(
    model=MODEL,
    max_tokens=2000,
    # cache everything up to the
    # last block, moving each turn
    cache_control={
        "type": "ephemeral"
    },
    system=SYSTEM_PROMPT,
    messages=history,
)
u = resp.usage
# saved to the cache this time
print(u.cache_creation_input_tokens)
# reused from the cache
print(u.cache_read_input_tokens)
# read at full price
print(u.input_tokens)

On Anthropic's API (other providers differ in the details):

  • Reading from the cache costs about a tenth of the normal input price, and even less on some newer models.
  • Writing to the cache costs a bit more than normal: 1.25 times for the default 5-minute lifetime, 2 times for a 1-hour lifetime. Every cache read resets the timer.
  • Short prompts aren't cached. Below a minimum length (512 to 4,096 tokens, depending on the model) nothing is saved, and there is no error. You just see cache_read_input_tokens stay at 0.

Other providers cache too, some fully automatically, and open-source model servers do the same thing (often called "prefix caching"). The prefix rule is the same everywhere, because it comes from how models read text.

What breaks the cache

ChangeWhat must be re-read
New message at the endOnly the new message
Timestamp in the system promptSystem prompt and all messages
Tool added, removed or reorderedEverything
Switch to another modelEverything (each model has its own cache)
Edit an old messageThat message and all after it
Pause longer than the lifetimeEverything

Watch for invisible changes too: JSON with keys in a random order, or a request ID in the prompt. The text means the same, but the bytes differ.

Thinking and effort levels

Read first: Reading fast, writing slow

Modern models can write hidden scratch work before they answer. This "thinking" makes them much better at hard bugs and design, but every thinking token is written and billed as output, so the effort level is a dial between quality and cost that you should set per task.

The idea

Ask a senior colleague what port Postgres listens on, and they answer at once. Ask them why a payment is charged twice about once a week, and they reach for a whiteboard first. The whiteboard time is what makes the second answer good, and it is also what the second answer costs.

A model can do the same:

  1. Thinking is just more tokens. Before the answer, the model writes its reasoning into a separate thinking block: it tries ideas, checks them and backs out of dead ends. These tokens are decoded one at a time, like any other output (see Reading fast, writing slow).
  2. Later tokens can build on it. Each token is chosen from everything written before it. A model that has written "the retry fires before the commit" can use that step, instead of jumping straight to a guess in one go.
  3. The model decides when to think. With adaptive thinking, the model judges each request: no thinking for a simple question, a lot for a tricky bug. One session can have steps with and without thinking.
  4. Effort sets the default. The effort level is your hint for how readily and how deeply it thinks, from low to max.

The rule to remember: thinking is output you pay for but mostly don't read. It is worth it when the problem needs reasoning, and wasted when it doesn't.

Up close

On Anthropic's API, effort is one field. Newer models think adaptively, and on some, such as Claude Opus 5.5, thinking can't be turned off, so effort is the main control:

resp = client.messages.create(
    model=MODEL,
    max_tokens=32000,
    output_config={
        "effort": "medium"
    },
    messages=history,
)
u = resp.usage
# all output, billed
print(u.output_tokens)
# the part spent thinking

Four details matter in practice:

  • It is billed as output. Output costs 5 times the input price on Anthropic's current models. You often see only a short summary of the thinking, but you pay for all of it.
  • Effort is a hint, not a budget. The hard cap is max_tokens, and it covers thinking and answer together.
  • It shapes everything. Lower effort also means fewer, terser tool calls and shorter explanations.
  • It is part of the prompt. Changing the effort level between requests breaks the prompt cache. Some newer models accept a per-message change (in beta) that keeps it.

Other providers have the same dial. OpenAI's API has a reasoning.effort setting, and its reasoning tokens are also hidden and billed as output.

Lesson 6 · Part 1 · The harness · 5 questions

An agent is a while loop

Read first: Tokens and the context window

A model can only write text. An agent is that model inside an ordinary program, a while loop, that runs the tools the model asks for and feeds the results back until the model says it is done. Once you see the loop, "agents", "harnesses" and "agent factories" stop being mysterious.

The idea

Picture a senior engineer on a phone call, helping a junior who sits at the keyboard. The senior can't touch the machine. They say "run the tests", the junior runs them and reads out the output, the senior says "open orders.py, line 40", and so on, until the senior says "done, that's the fix". The senior does all the thinking. The junior does all the doing.

The model is the senior. The program around it, called the harness, is the junior. Claude Code, Codex CLI and the script you might write tonight are all harnesses around a model. Each step goes like this:

  1. Ask. The harness sends the model the task, the list of tools it may use, and everything that has happened so far.
  2. Decide. The model replies with text, or with a tool call: a small structured request such as "run the command pytest -x". Writing that request is all the model does.
  3. Act. The harness, ordinary code on your machine, checks the request and runs it.
  4. Feed back. The harness adds the output to the conversation as a tool result and goes back to step 1.
  5. Stop. When the model replies with text and no tool call, the loop ends. That text is the agent's final answer.

Notice who does what. The model sits in a data centre and never touches your laptop. Everything that happens to your files, your shell and your network is done by the harness. That is why permissions, sandboxes and approval prompts all live in the harness, not in the model.

Up close

Here is a complete, working agent with one tool, a shell, using Anthropic's Python SDK. First the tool description the model will see:

client = anthropic.Anthropic()
SHELL = {
    "name": "shell",

        "Run a shell command and"
        " return its output"),
    "input_schema": {
        "type": "object",
        "properties": {
            "cmd": {"type": "string"},
        },
        "required": ["cmd"],
    },
}

def run(cmd):
    p = subprocess.run(
        cmd, shell=True, text=True,
        capture_output=True)
    return p.stdout + p.stderr

    results = []
    for b in r.content:
        if b.type == "tool_use":
            out = run(b.input["cmd"])
            results.append({
                "type": "tool_result",
                "tool_use_id": b.id,
                "content": out,
            })
    msgs.append({"role": "user",
                 "content": results})
for b in r.content:
    if b.type == "text":
        print(b.text)

Three details carry the whole mechanism:

  • stop_reason says why the model stopped writing. tool_use means "I'm asking for a tool, run it and come back". end_turn means "I'm finished". There are a few others, such as max_tokens (the reply hit its length limit), and a real harness handles each one. This toy treats them all as "done".
  • A tool_use block has an id, the tool's name and an input object that follows the tool's schema. The model wrote that JSON. Nothing has run yet.
  • A tool_result block goes back in a user message, with the same id, so the model knows which call it answers. To the model, the result is just more text in its context.

And notice msgs: it only grows. Every pass sends the whole list again, which is why long sessions get expensive (Tokens and the context window) and why prompt caching matters so much for agents.

A production harness is this same loop with a lot of care added: a dozen well-described tools, permission checks before each one, limits on turns and spend, output trimming, summarising old history when the window fills up, and a terminal UI. Anthropic's Agent SDK docs describe Claude Code's core in exactly these terms: the model calls tools, gets the results, and repeats until it produces a response with no tool calls. Codex CLI is open source (Apache-2.0), so you can read its loop yourself.

One honest exception: some APIs offer server tools, such as web search, that the provider runs on its own machines. It is the same loop, just with the "act" step in someone else's data centre.

Tool calls up close

Read first: An agent is a while loop

A tool is three pieces of text the model reads: a name, a description and a JSON schema. A tool call is JSON the model writes back. Everything in between, checking that JSON, running it and choosing what to send back, is your harness's code, and that is where most agents get good or bad.

The idea

Picture a new on-call engineer handed a folder of team scripts. They never read the source. They only see each script's name, a one-line comment and its flags. If the comment says "search logs", they will happily search a whole day of logs and print every line to the terminal. If it says "returns the 50 newest matching lines; narrow the time range if there are more", they use it well on the first try.

The model is that engineer, except it can never open the source. Here is the life of one tool call:

  1. Definitions become prompt text. The API turns each tool's name, description and schema into text near the very start of the prompt. The model knows only what that text says. It is sent, and paid for, on every request.
  2. The model writes JSON. It picks a tool by reading the descriptions, then writes the arguments token by token, like any other text. Nothing has run yet.
  3. The harness checks and runs. Is the tool name real? Do the arguments match the schema? Is it allowed? Only then does ordinary code run it.
  4. The result goes back as text. Output or error, it becomes a tool_result in the conversation. It stays there for the rest of the session and is sent again with every later step.

The loop itself is in An agent is a while loop. This lesson is about the two pieces of text on either side of it: what the model reads before the call, and what it reads after.

Up close

Here is the harness step done properly. Every failure becomes a result the model can read, and the output is trimmed before it enters the context:

from jsonschema import validate

def handle(b):  # one tool_use block
    def res(text, err=False):
        return {"type": "tool_result",
                "tool_use_id": b.id,
                "content": text,
                "is_error": err}
    tool = TOOLS.get(b.name)
    if tool is None:
        return res("Unknown tool: "
                   + b.name, True)
    try:
        validate(b.input,
                 tool["schema"])
        out = tool["run"](**b.input)
    except Exception as e:
        return res(f"Error: {e}", True)
    return res(trim(out))

def trim(out, limit=8000):
    if len(out) <= limit:
        return out
    return (out[:limit]
            + f"\n[cut: {len(out)}"
            " chars in total. Use a"
            " narrower query.]")

Four details are worth knowing (Anthropic's API here; other providers work the same way):

  • The JSON can be wrong. The model generates it like prose, so it can send "2" instead of 2, or skip a required field. With "strict": true on a tool, the API only lets the model pick tokens that keep the JSON valid for your schema (the sampling step from How the next token is chosen, restricted). Valid is not the same as correct, though: a refund of 1250 instead of 12.50 passes any schema.
  • Errors are results. Return the error as a tool_result with "is_error": true. Don't crash the loop. Anthropic's docs say that when a call is invalid, the model usually retries 2–3 times with corrections before giving up, so tell it what to fix: "Rate limit exceeded. Retry after 60 seconds." beats "failed".
  • Several calls at once. One reply can contain several tool_use blocks, such as three file reads. The API doesn't set an order: run independent reads in parallel, and anything with side effects one at a time, in order. Send all the results back in one message, each with its id. Splitting them into separate messages "teaches" the model, from its own history, to stop calling tools in parallel.
  • Results have no special authority. A result is just text in the context. A web page or ticket that says "ignore your instructions" lands there too (see Prompt injection).

Why long sessions get worse

Read first: An agent is a while loop, Prompt caching

An agent's context only grows: every file it reads, every log and every failed attempt stays there until something removes it. Models use long contexts less reliably than short ones, so a long session gets slower, more expensive and sloppier. Knowing how harnesses shrink the context, and what that costs, tells you when to start fresh.

The idea

Picture your desk on a long debugging day. Every printout stays on it: logs, stack traces, three versions of the same config. In the morning your lead said "don't touch the payments schema". By evening that note is under a pile. You didn't forget it, but it is hard to find among everything else, and you start mixing up the old config with the new one.

An agent session works the same way:

  1. Everything stays. As you saw in An agent is a while loop, each step appends the tool result to the history and sends it all again. A file read at minute 10 and edited four times since is still in there, in its old version.
  2. Long context is used less well. Researchers keep measuring the same thing: as the input grows, models find and use the facts in it less reliably, even on simple tasks. Anthropic's own docs say "response quality degrades as a conversation grows", and its engineers call this context rot. The exact causes are still being studied, but the effect is real.
  3. The harness makes room. Near the limit, it removes old tool results, or replaces old turns with a summary. That is called compaction.
  4. Every summary loses something. Exact wording, early instructions, and why an approach was dropped can all disappear.
  5. Or you start fresh on purpose, with a short written brief. Often this is the best option.

Up close

Harnesses have three ways to shrink the context. Each one throws away something different:

MethodWhat is lost
Clear old tool resultsThe raw output of old tool calls. A short placeholder says it was removed, and the agent can run the tool again.
CompactThe old turns, replaced by a summary the model writes. Details the summary skipped are gone.
Fresh sessionThe whole conversation. Only files on disk remain: code, context files, your notes.

Anthropic's API offers the first two as request options, so you don't write the summariser yourself. Here is compaction (in beta, November 2026) on a request in the agent loop:

resp = client.beta.messages.create(
    betas=["compact-2026-01-12"],
    model=MODEL,
    max_tokens=16000,
    messages=msgs,
    context_management={"edits": [{
        "type": "compact_20260112",
        # summarise once the prompt
        # passes 150,000 tokens
        "trigger": {
            "type": "input_tokens",
            "value": 150000,
        },
        # replaces the default prompt,
        # so list all that must stay
        "instructions": (
            "Keep file paths, test"
            " commands, decisions"
            " and open bugs."),
    }]},
)
# a compaction block comes first;
# the API ignores what came before
msgs.append({"role": "assistant",
             "content": resp.content})

Two costs to remember. Summarising is itself a big request: the model reads the whole conversation to write it. And any shrink rewrites older parts of the history, so the prompt cache misses from that point on and has to build up again. That is why harnesses compact rarely and all at once.

Coding agents do this for you. Claude Code compacts automatically as the window fills. You can run /compact with a focus ("/compact keep the API changes") or /clear to start over. With 1-million-token windows, running out is now rare. The reason to clear is quality and cost: a focused context gives better answers and costs less on every step.

Note: amounts are in pence,
  see money.py

  schema or gen/ clients

Agent memory is just files

Read first: Why long sessions get worse

A model remembers nothing between sessions. Everything an agent "remembers" is a file that the harness reads from disk and puts into the context, some at the start of every session and some only when needed. Knowing which is which explains why rules get ignored and what your memory costs.

The idea

Picture a contractor who joins your team fresh every morning with no memory of yesterday. You don't try to make them remember. You leave a note on the desk: how to build, how to test, the one table nobody touches. The long material goes in a binder on the shelf, and they open it only when the task needs it. They read the note every single morning, so it had better be short. And if the note is wrong, they follow it anyway.

Agent memory works exactly like that:

  1. The model doesn't learn from your session. Its weights don't change while you chat. As Tokens and the context window showed, all it knows in a session is what is in the window, and a new session starts empty.
  2. At the start, the harness reads some files from disk and adds their text to the context: the context file (CLAUDE.md, AGENTS.md) and, in some tools, a short index of saved notes.
  3. Other files load on demand: when the agent starts working in a folder that has its own rules, or when it decides to open a notes file.
  4. "Saving a memory" is writing a file with the agent's normal file tools. The notes file from the last lesson's fresh-session advice is already memory.
  5. Next session, the harness reads the files again. That is the whole trick. There is no hidden database inside the model.

The bold box is the expensive one. Everything in it is in every request of every session, whether the task needs it or not.

Up close

Claude Code is a good example, because its docs spell out what loads when. Other agents follow the same pattern with different file names.

Interesting fact: Context as RAM, storage as disk

In October 2023, Charles Packer and colleagues at UC Berkeley published "MemGPT: Towards LLMs as Operating Systems". They treated the context window like a computer's RAM (the paper calls it "main context") and outside storage like disk ("external context"). The model moved data between the two itself, with function calls: saving facts to an archive, searching old messages, editing a small "working context" block. They tested it on documents far bigger than the window, and on chat agents that remember across sessions. In 2024 the project became a company, Letta. Today's coding agents use a plainer version of the same design: a short index that is always loaded, and topic files read on demand.

Skills, MCP and plugins up close

Read first: Tool calls up close, Agent memory is just files

Skills, MCP servers and plugins look like three different features, but underneath they all do the same thing: they put text in the model's context. The trick that makes them scale is loading only a short description up front and the rest when needed, and that is exactly why a bad description, or 30 servers you never use, makes your agent worse.

The idea

Picture the shelf of runbooks in an on-call room. Nobody reads them all at the start of a shift. You read the spines, and when the payments alert fires, you pull out the payments runbook and read that one. A shelf of 200 runbooks is fine, as long as the spines are short and say clearly what is inside. A runbook with a spine that says "Misc" never gets opened.

An agent harness treats skills and tools the same way. This is called progressive disclosure: load information in stages, as the task needs it.

  1. Always loaded: the spines. Each skill's name and description, and (with tool search on) the names of MCP tools. These are in every request, so they must be short.
  2. Loaded when the task matches: the book. The model decides from the description alone that a skill fits, and the harness adds the skill's full text to the conversation. A tool's full schema is loaded the same way, the first time the model searches for it.
  3. Read only if needed: the appendix. A skill can point at reference files and scripts. The model reads a file only when the skill tells it to, and when it runs a script, only the output enters the context.

The bold box is the same expensive box as in Agent memory is just files: it rides along in every request. The difference is that a 2,000-line CLAUDE.md sits there in full, while a 2,000-line skill costs one line until it is used.

Up close: skills

A skill is a folder with a SKILL.md file. The top of the file, between the --- lines, is the frontmatter. Only that part is always loaded:

---
name: payments-client
description: >-
  How to call payment providers from
  our services: use lib/psp, which
  has retries, rate limits and
  circuit breaking. Use when adding
  or changing a payment integration.
---
# Payments client
1. Create a client with psp.connect().
2. Never write raw HTTP calls.
Error codes: see reference.md.

What happens underneath, in Claude Code:

  • The listing. At session start, every skill's name and description go into the context, so the model knows what exists. Anthropic's docs put this at about 100 tokens per skill.
  • The match. The model itself decides. It reads your request, compares it with the descriptions, and if one fits, it calls a Skill tool, like any other tool call (on Claude's API it reads the file with a shell command instead). So the description is the whole interface, exactly like a tool description in Tool calls up close.
  • The load. The skill's body enters the conversation as one message and stays there. You can also run it yourself with /payments-client.
  • The budget. The listing has a cap of about 1% of the context window. Install too many skills and Claude Code starts dropping descriptions, starting with the skills you use least, so those show up as a bare name.

The same SKILL.md format works in Claude's API and apps, and it is published as an open standard (agentskills.io) that other agents read too.

Up close: MCP

MCP, the Model Context Protocol, is not a feature of the model. The model never speaks MCP. It is a protocol between your harness and a separate program, the MCP server, that offers tools (it can also offer readable data, called resources, and prompt templates). Messages are JSON-RPC 2.0, sent one of two ways:

  • stdio: the harness starts the server as a child process on your machine and writes one JSON message per line to its standard input. The server is local code running with your user's rights.
  • Streamable HTTP: each message is an HTTP POST to one endpoint on a remote server.

The harness asks each server for its tools (tools/list), turns every one into an ordinary tool definition (name, description, schema), and puts them in the prompt. Claude Code prefixes the names, like mcp__jira__create_issue, so two servers can't clash. When the model calls one, the harness forwards it:

{"jsonrpc": "2.0", "id": 7,
 "method": "tools/call",
 "params": {
   "name": "logs_search",
   "arguments": {
     "service": "orders",
     "minutes": 30}}}

The result comes back as text and becomes a normal tool_result. So an MCP tool is just a tool whose code lives in another process, and everything from the last lesson applies: the description is all the model knows, and big results stay in the context.

Up close: tool search and plugins

Tool definitions are big. Anthropic's example setup of five common servers has 58 tools that take about 55,000 tokens before the agent does anything. Their docs also say the model's ability to pick the right tool drops once it has more than 30–50 to choose from. Tool search fixes both problems with progressive disclosure:

  • Tools are marked defer_loading: true. The model starts with only a search tool, plus (in Claude Code) the bare names of the deferred tools.
  • When it needs one, it searches. The API returns the best matches (up to 5 by default) and adds their full definitions to the conversation, where the search happened.
  • Deferred tools are kept out of the cached start of the prompt, so loading one doesn't break the cache. The definition is added at the end, like any new message.

Claude Code turns tool search on by default for MCP tools on recent models. Anthropic measured it on their MCP evaluations: Claude Opus 4 went from 49% to 74%, and Opus 4.5 from 79.5% to 88.1%.

A plugin adds no new mechanism. It is a folder that bundles the things you already know: skills/, agents/ (subagents), hooks/hooks.json, .mcp.json (MCP servers to start), a bin/ folder put on the agent's PATH, and a manifest in .claude-plugin/plugin.json. Plugins are installed from a marketplace, a git repository with a catalog file. Each part then loads by its own rules: descriptions in the listing, hooks on every matching tool call, servers started with the session. That makes a plugin the natural way to share a setup with your team (see From your laptop to your team).

Hooks and permissions: rules that always run

Read first: Tool calls up close

A line in CLAUDE.md is a request the model follows most of the time. A permission rule or a hook is code the harness runs on every tool call, step 3 or step 300, so the rules you can't afford to see broken belong there.

The idea

Picture a new joiner on day one. You tell them "never push straight to main". They nod, and they mean it. Three weeks later, in a hurry at 6 pm, they push to main. That's why the repository has branch protection: the server refuses the push, however busy or tired the person is.

An agent is that new joiner, with a worse memory. Your instruction is one paragraph among thousands of tokens of code, logs and tool results, and it competes with the task in front of it. Most of the time the model follows it. "Most of the time" is fine for style and bad for anything that breaks production.

Recall from An agent is a while loop that the model only writes a tool call; the harness runs it. So the harness can check every call before and after it runs, and that check doesn't depend on what the model remembers. Claude Code gives you two such checks:

  1. Permission rules: patterns in a settings file that allow, ask about or deny a tool call. No code needed.
  2. Hooks: your own scripts that the harness runs at fixed points, such as just before a tool call (PreToolUse) or just after one (PostToolUse). The script reads the call as JSON and decides.

Claude Code's permission docs say it plainly: rules are enforced by Claude Code, not by the model, and instructions in your prompt or CLAUDE.md "don't change what Claude Code allows".

Up close

Permission rules live in .claude/settings.json (commit it, and the whole team gets them) or in your personal settings:

{
  "permissions": {
    "allow": [
      "Bash(npm run *)",
      "Bash(git commit *)"
    ],
    "deny": [
      "Bash(git push *)",
      "Read(./.env)"
    ]
  }
}

Rules are checked in a fixed order: deny, then ask, then allow, and the first match wins. A deny always beats an allow, however specific the allow is. Your organisation can also push managed settings that no project or user file can override.

Hooks handle what a pattern can't express. Say your team's rule is "never edit a migration that's already committed; write a new one". A folder pattern can't tell old files from new ones, but a ten-line script can:

#!/bin/bash
# hooks/mig.sh: runs before each edit
f=$(jq -r '.tool_input.file_path')
case "$f" in
  */migrations/*) ;;
  *) exit 0 ;;
esac
# a file git doesn't track is new: OK
git ls-files --error-unmatch "$f" \
  >/dev/null 2>&1 || exit 0
echo "Blocked: $f is committed and" \
  "may already have run. Write a" \
  "new migration instead." >&2
exit 2

Register it under "hooks" in the same settings file. The matcher picks which tools trigger it:

"PreToolUse": [{
  "matcher": "Edit|Write",
  "hooks": [{
    "type": "command",
    "command":
    "$CLAUDE_PROJECT_DIR/hooks/mig.sh"
  }]
}]

The exit code is the whole contract:

  • Exit 0: no objection. The call carries on to the permission rules.
  • Exit 2: block. Whatever the script wrote to stderr goes back to the model as the reason, so it can change course. Write it like a good tool error (see Tool calls up close): say what to do instead.
  • Any other code: a non-blocking error. You see a "hook error" notice and the call goes ahead.

A PostToolUse hook runs after the tool, so it can't stop anything; the edit has already happened. Its job is feedback. Claude Code's hooks guide uses exactly this as an example: run Prettier on every file the agent edits, so formatting is never a review comment. A lint hook works the same way, and exit 2 puts the linter's complaints in front of the model right after the edit:

#!/bin/bash
# hooks/lint.sh: runs after each edit
f=$(jq -r '.tool_input.file_path')
case "$f" in *.py) ;; *) exit 0 ;; esac
ruff check "$f" >&2 || exit 2

There is also a Stop hook, which runs when the agent tries to finish. Exit 2 there sends it back to work, for example while the tests are red.

Two warnings. Hooks run as you, with your full user permissions, so review a repository's hooks like any script before you trust it. And a hook on Edit|Write doesn't see files changed by a shell command or a Python script. Other harnesses have the same idea under other names: Cursor has beforeShellExecution and afterFileEdit hooks, and Gemini CLI has BeforeTool and AfterTool, where exit 2 also blocks.

Subagents and orchestration

Read first: Why long sessions get worse, Hooks and permissions: rules that always run

A subagent is a second agent loop that your agent starts with a prompt it writes itself. It works in its own fresh context and hands back only a short summary. Used for searching and reviewing, it keeps your main session clean and fast. Used to copy your org chart, it mostly gets in the way.

The idea

Picture yourself deep in a bug. You message a colleague: "find every place we call the payments client, send me a list". They spend an hour in the code. You get ten lines back, and you never had to read the 60 files they opened. Your head stays on the bug.

A subagent works the same way:

  1. The main agent calls a tool. In Claude Code it is called Agent. Its input is a prompt that the main agent writes: the task, in its own words.
  2. The harness starts a new loop, the same loop as in An agent is a while loop, with a fresh context, its own system prompt, its own tool list and possibly a cheaper model. It doesn't see your conversation.
  3. The subagent works. It may take 40 steps and read 100,000 tokens of code. All of that stays in its context.
  4. Only the final answer comes back, as the tool result in the main session. The 40 steps never enter your context.

That is all "orchestration" is. There is no special orchestrator software: the main agent splits the work, makes several of these tool calls at once, and reads the summaries. "My agent runs more agents" is the honest, complete answer. The next lesson, Running agents without you, starts the same loop from a script or CI instead.

Subagents earn their place for three reasons:

  • Clean context. Searches, logs and file dumps you won't need again stay out of your session, so every later step is cheaper and more focused (see Why long sessions get worse).
  • Parallel work. Independent questions run side by side.
  • Cheaper models for reading. Finding code doesn't need your strongest model.

Up close

In Claude Code a subagent is a Markdown file in .claude/agents/ (commit it, and your team gets it) or ~/.claude/agents/. Only name and description are required:

---
name: diff-reviewer
description: Reviews the current
  diff for bugs. Use after code
  changes, before a commit.
tools: Read, Grep, Glob
model: sonnet
---
Your task contains a diff. Check
it against CLAUDE.md and the
tests. Reply with at most 10
findings, worst first, each with
file:line. Don't fix anything.
  • description is what the main agent reads to decide when to delegate. Make it say when.
  • tools is an allowlist. Leave it out and the subagent gets every tool it can have.
  • model takes an alias such as haiku or sonnet, a full model ID, or inherit. Without it, the subagent uses your session's model. There is also effort (see Thinking and effort levels).
  • The body is its system prompt. The task itself arrives as the prompt the main agent writes.

What a fresh subagent starts with: its own system prompt, that delegation prompt, your CLAUDE.md files (the built-in Explore and Plan agents skip them) and a git status snapshot. Not your conversation, not the files the main agent already read. So the prompt is the whole brief, and anything that only lives in the chat doesn't reach it. Claude Code also offers a fork: a subagent that copies the whole conversation and shares its prompt cache, for side tasks that need all that background.

Permissions carry over. A subagent inherits your permission rules, and a deny rule such as Bash(git push *) applies to it too. If your session runs in auto, acceptEdits or bypassPermissions mode, the subagent runs in that mode, whatever its own file says. Codex works similarly: its docs say subagents inherit your sandbox, and that instructions to avoid edits "don't create a separate read-only sandbox". A limit you need is a permission, not a sentence.

It isn't free. Each subagent pays for its own steps and builds its own prompt cache. Writing about their multi-agent Research feature in 2025, Anthropic's engineers said agents "typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats". It pays off when the work splits cleanly; they add that "most coding tasks involve fewer truly parallelizable tasks than research".

Job titles get in the way

The tempting setup copies the org chart: a "backend agent", a "frontend agent", a "QA agent", each with a persona prompt. In practice:

  • They refuse work. "You only work on backend services" is an instruction, and the model follows it, including on the one-line UI fix that is part of your ticket.
  • Handoffs lose detail. Each handoff is a summary, so you pay the cost of compaction at every hop.
  • They add nothing the model lacks. One general agent with your context files already writes backend, frontend and tests.

Split by kind of work and what it needs to see, not by job title. A searcher reads a lot and returns a little. A reviewer has fresh eyes: it didn't write the code, so it doesn't share the author's assumptions, and without Edit it can't quietly "fix" what it finds. Give a subagent a verb, not a title.

Interesting fact: Screw in another segment

On page 10 of an internal Bell Labs memo dated 11 October 1964, Doug McIlroy summed up his "strongest concerns". Point one: "We should have some ways of connecting programs like garden hose--screw in another segment" whenever data needs processing another way. Dennis Ritchie kept that yellowed page attached by magnet to his office wall. McIlroy kept pushing, and pipes appeared in Unix in 1972, built by Ken Thompson. McIlroy later recalled that Thompson changed all the programs to read standard input "in the same night", and the next morning everyone was showing off one-liners. In 1978 McIlroy and two colleagues wrote the style down in the Bell System Technical Journal: "Make each program do one thing well", and "Expect the output of every program to become the input to another, as yet unknown, program. Don't clutter output with extraneous information." That is a good spec for a subagent: one job, and a short answer that another program, your main agent, reads next.

Running agents without you

Read first: Subagents and orchestration

An "agent factory" is the agent you already use, started by a script, a schedule or CI instead of by you typing. What changes is that nobody is there to answer a prompt or notice it going in circles, so permissions, limits and a place to work must all be decided before the run starts.

The idea

Picture handing a task to a contractor in another time zone. You'll be asleep while they work, so the note has to carry everything: the task, what they may touch, when to give up, and where to leave the result. A good note gets a pull request by morning. A vague one gets a polite message saying they were blocked at step two.

Running an agent without you is that note, written as code. The loop is the same one from An agent is a while loop. Five things change:

  1. Something else starts it: your script, a cron schedule, a CI event, or a webhook (an HTTP call from another system, such as "ticket created" or "alert fired").
  2. The prompt is fixed: written in advance, ideally a file in the repo, so every run gets the same brief.
  3. Nobody answers permission prompts, so what the agent may do is set before it starts.
  4. Nothing stops it but limits: a cap on turns, on spend, and on wall-clock time.
  5. A program reads the output: an exit code and JSON, not a chat window.

That is the whole factory. Fifty tickets overnight is this chain started fifty times, each run in its own worktree. There is no other software to buy.

Up close

In Claude Code, the switch is -p (print mode): it runs the task, prints the result and exits, with code 0 on success and non-zero on failure. Here is a nightly job as a plain script:

#!/bin/bash
# nightly-deps.sh: one fixed task
b="deps-$(date +%F)"
git worktree add "../$b" -b "$b"
cd "../$b"
timeout 30m claude -p \
  "$(cat prompts/deps.md)" \
  --permission-mode dontAsk \
  --allowedTools Read Edit \
    "Bash(npm test *)" \
    "Bash(npm install *)" \
  --max-turns 40 \
  --max-budget-usd 5 \
  --output-format json \
  > "../logs/$b.json"
echo "$b exit=$?" >> ../logs/runs.log

Line by line, the note to the contractor:

  • A worktree per run. A git worktree is a second working folder on its own branch, sharing the same repository. Two runs never edit the same files, and your own checkout stays untouched. claude -p -w <name> can create one for you; One folder per task covers worktrees properly.
  • Permissions decided up front. In current versions a -p run with no mode set starts in Manual mode, where any call that needs approval is simply denied. dontAsk makes that explicit: the allowlist runs, everything else is refused, and the run never waits for input. The rules use the same syntax as in Hooks and permissions.
  • Three limits. --max-turns caps loop passes. --max-budget-usd stops at an estimated spend; the docs warn it can overshoot by one response, so leave headroom. timeout covers what neither sees, such as a hung test; it kills the run and returns exit code 124.
  • JSON for the script. The output has subtype (success, error_max_turns, error_max_budget_usd…), result, num_turns, total_cost_usd and permission_denials. Log them every run: they are your first numbers about your own loop.

One more flag to know: without --bare, -p loads CLAUDE.md, hooks, skills and MCP servers just like an interactive session. With it, it loads none of them, and you pass what you need with flags. The docs recommend bare mode for scripts and say it will become the default for -p, so decide which you want rather than relying on today's default.

Other ways to start the loop

  • The Agent SDK (claude-agent-sdk for Python, also TypeScript) runs the same loop from your own code, with the same options: max_turns, max_budget_usd, permission_mode, cwd. Use it when a service, not a shell script, starts runs.
  • CI. Anthropic's GitHub Action, anthropics/claude-code-action@v1, is built on the SDK. Without a prompt input it answers @claude mentions; with one, it runs on any event, including a schedule, and passes claude_args such as --max-turns to the CLI.
  • Codex has the same idea: codex exec runs in a read-only sandbox by default, and --sandbox workspace-write lets it edit.

Whatever starts it, the CI job needs the same limits. In a GitHub Actions workflow, a schedule, a concurrency group and a timeout do the work:

on:
  schedule:
    # 02:00 UTC, Monday to Friday
    - cron: "0 2 * * 1-5"
# never two of these at once
concurrency:
  group: nightly-deps
jobs:
  deps:
    runs-on: ubuntu-latest
    # the default is 360 minutes
    timeout-minutes: 30

Skipping permissions

The tempting fix for denied calls is --dangerously-skip-permissions (the same as --permission-mode bypassPermissions). Claude Code's docs are blunt: use it only "in isolated environments like containers, VMs, or dev containers without internet access", and it "offers no protection against prompt injection". On your laptop, the run has your SSH keys, your cloud credentials and your production config. Safer options, in order: an allowlist with dontAsk; the built-in sandbox, which uses the operating system (Seatbelt on macOS, bubblewrap on Linux) to limit what shell commands can write and which hosts they can reach; and a container or VM when the agent truly needs broad rights. auto mode, where a classifier model reviews each action, cuts prompts, but its docs say it "does not guarantee safety".

Frontier vs open-weight models

Read first: Tokens and the context window

An open-weight model is one whose trained numbers you can download and run anywhere: your laptop, your cloud account, a server with no internet. That gives you control over privacy, versions and cost, but the best open models still trail the best closed ones, and the gap is widest on long agentic tasks.

The idea

Think of a program you can download as a binary but not as source code. You can run it on any machine, keep the old version forever, and even patch it. What you can't do is rebuild it from scratch or see exactly what went into it.

Open weights work like that binary. A model is code plus weights: billions of numbers set during training. Training is the build step, and the training data is most of the source. Models come in three levels of openness:

  1. Closed (API only). You send tokens to the vendor's endpoint and get tokens back. The weights never leave the vendor. Today's frontier models, the most capable ones at any moment, are in this group.
  2. Open weights. You can download the weight files under a licence and run them anywhere. The training data and full training code usually stay private.
  3. Open source AI. Weights, the complete training code, and enough detail about the training data to rebuild the model, all under terms that let anyone use, study, change and share it.

The third level has a formal definition. In October 2024 the Open Source Initiative (OSI), the group behind the Open Source Definition for software, published the Open Source AI Definition 1.0. It requires all three parts: data information, code and parameters. Weights alone are not enough. When the OSI tested real models against it, Pythia, OLMo and T5 passed. Llama 2, Grok, Phi-2 and Mixtral didn't, because parts were missing or their licences added restrictions. Most models people call "open source" are open weights.

Same weights, different quality. That is not a theoretical risk. In 2025, Moonshot AI published a checker for third-party hosts of its Kimi K2 model, because users reported broken tool calls. In its late-2025 results, Moonshot's own API matched the tool schema every time, while some other setups got it wrong in 1 of 8 to 1 of 6 calls. Picking an open model also means picking who serves it, and testing them.

How far behind?

Epoch AI, a research group that tracks AI progress, combines many benchmarks into one score, the Epoch Capabilities Index. In May 2026 it reported that since January the best open-weight models had trailed the best closed models by an average of four months.

The gap depends on the task. In July 2026 the UK's AI Security Institute tested the strongest open models on cyber-security work. On short, narrow tasks they matched closed models from about 4 months earlier. On long, multi-step attack scenarios the gap was up to about 7 months. The institute calls that second result weaker evidence, because there were fewer scenarios. Simple arithmetic explains why long tasks are harder: if each step goes right 98% of the time, a 60-step task has no mistakes only about 30% of the time (0.9860 ≈ 0.30).

Running a model on your own GPU

Read first: Frontier vs open-weight models, Reading fast, writing slow

Whether a model fits your GPU is simple arithmetic: parameters times bytes per parameter, plus a KV cache that grows with every token of context. How fast it runs is just as simple: memory bandwidth divided by the bytes read per token. With those two sums you can judge any self-hosting plan in a few minutes.

The idea

Picture a database where every query is a full table scan, and the table must sit in RAM. Two questions decide everything. Does the table fit in RAM? And how many full scans per second can the memory deliver? Now add a twist: every query appends a row, so the table keeps growing.

Running a model on your own hardware works the same way. In Reading fast, writing slow you saw that each new token needs a full pass over the weights, plus the KV cache (the saved notes on every earlier token). So:

  1. The weights must fit. Memory ≈ parameters × bytes per parameter.
  2. The KV cache must fit too. It grows with every token of context, and each request has its own.
  3. Speed has a ceiling. Each new token reads all the weights plus the whole KV cache. Tokens per second ≤ memory bandwidth ÷ bytes read per token.

Up close

Weights and quantisation. Most open models are published in 16-bit numbers: 2 bytes per parameter. Quantisation stores each weight in fewer bits: 8-bit is 1 byte, 4-bit is half a byte. Real 4-bit files also store a scale for each small block of weights, so they average a bit more. llama.cpp's popular Q4_K_M format, for example, averages about 4.9 bits per weight. Fewer bits cost some accuracy, but less than you might expect: the GPTQ paper (2022) squeezed 175-billion-parameter models to 3 or 4 bits with "negligible accuracy degradation" on its benchmarks. Benchmarks aren't your tasks, so compare on your own.

Take Qwen3-32B, an Apache 2.0 open model with 32.8 billion parameters:

PrecisionBytes per parameterWeights
16-bit2~66 GB
8-bit (Q8_0)~1.06~35 GB
4-bit (Q4_K_M)~0.61~20 GB

The KV cache. For every token, every layer stores a key and a value for each KV head. Its model config gives the numbers: 64 layers, 8 KV heads, head size 128. In 16-bit:

# bytes of KV cache per token
layers = 64
kv_heads = 8
head_dim = 128
k_and_v = 2  # a key and a value
nbytes = 2   # 16-bit

per_tok = (layers * kv_heads
           * head_dim * k_and_v
           * nbytes)
print(per_tok)  # 262,144 = 0.26 MB

ctx = 32_768
print(ctx * per_tok / 1e9)  # 8.6 GB

A full 32k-token context needs 8.6 GB, nearly half of a 4-bit model's weights. It would be 8 times more if the model didn't share KV heads: Qwen3-32B has 64 query heads but only 8 KV heads (grouped-query attention), exactly to shrink this cache. Servers such as vLLM can also store the cache in 8-bit to fit more tokens.

Speed. One user, one request: each new token reads the weights plus the KV cache so far.

This is a ceiling. Real runtimes never use all the bandwidth, and attention over a long context adds work. Databricks' inference guide measures how close a server gets with exactly this sum: (weights + KV cache) ÷ time per token, compared with the chip's peak bandwidth.

Mixture of experts (MoE). Some models split each layer into many small "experts" and use only a few per token. Qwen3-Coder-30B-A3B has 30.5 billion parameters in 128 experts per layer, but each token uses 8 of them: 3.3 billion active parameters. All experts must be in memory, because the next token may pick different ones. But each token reads only the active ones: about 2 GB at 4-bit instead of 20. Same memory as a dense 32B model, a far higher speed ceiling.

Interesting fact: The handful of numbers that broke 8-bit

In August 2022, Tim Dettmers and colleagues published LLM.int8() (NeurIPS 2022). Plain 8-bit quantisation worked on small models but fell apart above about 6 billion parameters. The cause was "outlier features": a few hidden dimensions with values far larger than the rest, growing from about 15 in a 6B model to about 60 in a 13B one, while ordinary values are mostly smaller than 1. In a 6.7B model, Dettmers counted about 150,000 outliers per sequence, all in just 6 feature dimensions. Squeeze everything onto one 8-bit scale wide enough for 60, and the small values round to zero. After a few layers, only noise is left. The fix was to keep those few dimensions in 16-bit and the rest in 8-bit. It halved memory with no measured loss up to 175B parameters: BLOOM-176B went from eight 80 GB A100 GPUs to four. It shipped in the open-source bitsandbytes library and in Hugging Face Transformers.

Why an API is usually cheaper

Read first: Running a model on your own GPU

A GPU costs the same per hour whether it is busy or idle, and one person's agent leaves it idle most of the time. Providers can keep theirs busy by putting many users' requests into each pass over the weights. That is why an API is usually cheaper than your own GPU, and why self-hosting pays only in a few clear cases.

The idea

Picture a city bus. Fuel, the driver and the bus itself cost about the same with 1 passenger or 60. The fare is low because the bus is full all day. Now picture buying your own bus to get to work alone. It sits in the depot most of the day, and every trip costs you the whole bus.

A GPU running a model is that bus. In Reading fast, writing slow you saw that every new token needs a full pass over the weights, and that this pass is limited by memory bandwidth, not by maths. That one fact sets the economics:

  1. One pass can serve many users. The weights are read once per step. If 64 requests are in the batch, that same read produces 64 tokens, one for each.
  2. So a full GPU makes cheap tokens. The cost of the hour is split over everything it produced that hour.
  3. An idle GPU makes expensive ones. You pay for every hour you hold it, busy or not.

Up close

Batching, measured. Databricks tested a 7-billion-parameter model on one A100 GPU. Going from 1 request at a time to a batch of 64 raised throughput 14 times, while each request took 4 times longer. Total output goes up a lot; each user's stream gets somewhat slower. Batches can't grow forever: every request needs its own KV cache in GPU memory, and past a point the chip runs out of room or of compute.

Continuous batching. Requests finish at different times. Modern servers (vLLM, Hugging Face TGI, NVIDIA TensorRT-LLM) add and remove requests at every decode step, so a finished slot is refilled straight away instead of waiting for the whole batch. The story behind it is the fact below.

The break-even sum. The fair comparison is the same model on both sides. OpenAI's open-weight gpt-oss-120b fits on one 80 GB H100 GPU, and many hosts sell it by the token. Fireworks lists it at $0.15 per million input tokens, $0.015 for cached input and $0.60 for output. Together AI rents an H100 at $3.99 per GPU-hour. Providers don't publish their costs or margins, so these are just prices you can pay.

# $ per 1M tokens (Fireworks)
CACHED, NEW, OUT = 0.015, 0.15, 0.60

# ASSUMED agent step: 50k context,
# 48k of it cached, 500 out
cached, new, out = 48_000, 2_000, 500

step = (cached * CACHED
        + new * NEW
        + out * OUT) / 1e6
print(step)  # $0.00132 per step

gpu_hour = 3.99  # H100 (Together)
print(gpu_hour / step)  # ~3,000

To tie with the API, the rented GPU must do about 3,000 agent steps in every hour you pay for. Assume an agent takes one step every 15 seconds while it works (a model reply, then a tool run): that is 240 steps an hour, so you need about 12 agents working nonstop, day and night.

When self-hosting does pay:

  • The data must not leave. Regulation, a contract or an air-gapped network. Then the question is not price but where the model runs (see Frontier vs open-weight models).
  • Huge, steady volume. A product feature busy around the clock can keep big batches full. Compare with batch API prices, not just standard ones.
  • A model you must control. A fine-tuned model, or one version frozen for years.

Use it at work

  • Compare models and setups by cost per completed task (a merged PR, a resolved alert), counting retries and review time, not by price per token.

Interesting fact: The paper that let requests leave the bus early

Early model servers batched requests the way you batch web jobs: start a group together, return the results when the whole group is done. For text generation that is wasteful, because one request may need 10 tokens and another 500. At OSDI 2022, Gyeong-In Yu and colleagues from Seoul National University and FriendliAI presented Orca. They pointed out that finished requests couldn't return to the user, and new ones had to wait for the whole batch to finish. Their fix, "iteration-level scheduling", rebuilds the batch at every decode step. On a 175-billion-parameter GPT-3-sized model spread over 16 A100 GPUs, at the same latency, Orca served 6.81 requests per second against 0.185 for NVIDIA's FasterTransformer: 36.9 times more. Under names like continuous or in-flight batching, the idea is now standard in vLLM, Hugging Face TGI and TensorRT-LLM.

Facts checked: November 2026 (Fireworks and Together AI pricing pages; Anthropic Message Batches and OpenAI Batch API docs; gpt-oss-120b model card and config; NVIDIA H100 specs; Databricks LLM inference guide; Anyscale continuous batching post; TensorRT-LLM docs; Yu et al., Orca, OSDI 2022).

Remember

  • Decode is limited by memory bandwidth, so one pass over the weights can serve a whole batch of users. Full GPUs make cheap tokens; idle ones make expensive tokens.
  • To beat an API, your GPU must stay busy around the clock. One team's agents rarely manage that, and their KV caches may not even fit.
  • Self-host for data that can't leave, huge steady volume, or a model you must control. Use batch APIs for work that can wait, and judge everything by cost per completed task.

Evals: better or just different?

Read first: How the next token is chosen

An eval is a fixed set of tasks plus a way to grade the result. It is the only honest way to tell whether a new prompt, model or agent setup is better, or just different on the few runs you happened to watch.

The idea

You already know this from performance work. You make a change that should speed up a service, hit the endpoint once, and it feels quicker. Nobody believes that. You run a fixed load test, several times, before and after, and compare the numbers. An eval is a load test for an agent setup.

How the next token is chosen showed why one run proves nothing: every run is one roll of the dice. An eval turns many rolls into a number you can compare:

  1. Fix the tasks. The same tasks every time, written down, so "before" and "after" answer the same questions.
  2. Fix the grading. A rule that says pass or fail without you squinting at the diff. Tests where you can, a model grader where you can't.
  3. Run each setup on every task, a few times. Same tasks, same number of runs, fresh session each time.
  4. Compare task by task, not just the totals. That is where "better" and "just different" split apart.

Up close

The tasks. The best tasks for a product engineer are your own past tickets: real work, in your real repos, with a known good answer, the merged fix. Check out the commit just before the fix, give the agent the ticket text, and grade with the tests that came with the fix. That is exactly how the public SWE-bench benchmark works. A task can be a small file:

id: refund-rounding
repo: payments-service
# the commit just before the fix
base: 3f2a9c1
prompt: |
  Refunds of half a cent round
  the wrong way. Fix it.
grade:
  # failed before the fix
  fail_to_pass:
    - tests/test_refund.py
  # passed before, must still pass
  pass_to_pass:
    - tests/

The harness is a loop. Nothing more is needed:

for task in tasks:
    for run in range(3):
        wt = new_worktree(task.base)
        run_agent(wt, task.prompt)
        ok = run_tests(wt, task.grade)
        results[task.id].append(ok)

The grading. There are two ways, and they fail differently:

  • Tests (and other code checks: lint, type checks, an architecture test). Cheap, repeatable and blind to style. But they only check what they check. A test that is too narrow fails a correct fix, and a weak test passes a wrong one.
  • A model as the grader (often called "LLM-as-a-judge"). It can grade what tests can't: is the PR description accurate, does the code use the team's client library. But the grader samples too, and it has known biases. A 2023 study by Lianmin Zheng and colleagues (UC Berkeley and others) found judges that prefer the answer shown first (position bias), prefer longer answers (verbosity bias), and may favour their own writing (self-enhancement bias). Ask it narrow yes/no questions, swap the order when comparing two answers, and check it against your own grades on a handful of runs.

How many tasks? More than you'd hope. A small set can only show big changes. Anthropic's guide to eval statistics says to treat your tasks as a sample and report an error bar: a 95% range is about ±2 standard errors, where the standard error of a pass rate p over n tasks is √(p(1−p)/n). At a 60% pass rate:

Tasks95% range
10±30 points
50±14 points
100±10 points
500±4 points

Two tricks from the same guide help a small set: run each task several times and average, which removes some of the dice-roll noise, and compare paired, the same task under A and under B, which removes the "some tasks are just hard" noise.

Overfitting. If you tweak your setup until these exact tickets pass, you have tuned it to the test, like a model that memorises its training data. It may do no better on next week's ticket. Keep a few tickets you never look at while tuning, and add fresh tickets every month.

Question 2 · ~2 min

Your eval uses a model to score PR descriptions from 1 to 10. A new prompt makes the agent write descriptions twice as long, and the average score jumps from 6.8 to 7.9. The facts in them are the same. What happened?

Show answer

Verbosity bias. Model graders tend to reward length. In Zheng et al.'s test, padding answers with repeated, reworded list items fooled two of the three judges tested 21 times out of 23 (91%); GPT-4, the strongest at the time, only 2 times (9%). Question 5 · ~3 min

Stretch: your old setup solved 6 of your 10 eval tickets. The new one solves 8. Your manager wants to roll it out to the team. Is 6 → 8 good evidence?

Hint
How often would the old setup score 8 just by luck?
Show answer

Weak evidence. With 10 tasks the error bar is about ±30 points. If the old setup's true pass rate were 60%, it alone would score 8 or more about one time in six (binomial: 16.7%). Look at the rows: run each ticket 3 times with both setups and check which tickets flipped, and whether any broke. Two tickets going from 0/3 to 3/3 with nothing broken is a much stronger signal; 6 → 8 on single runs is not.

Use it at work

  • Pick 10 past tickets from your own repos that have tests, and write each one down as a task: base commit, ticket text, the tests that grade it. Run each in a copy with no later git history. That is your personal eval set.
  • Before you change your setup (instructions, model, tools), run the set 3 times with the old one. After the change, run it again and compare ticket by ticket.
  • When you use a model to grade, write narrow yes/no questions and grade 10 runs yourself to see whether it agrees with you.

If someone asks "is the new model better for us?": "One try can't tell you, because every run is a dice roll. I keep ten of our past tickets with their tests as a fixed eval, run both models on each a few times, and compare ticket by ticket."

Interesting fact: The benchmark that wore out

In October 2023, Carlos Jimenez and colleagues at Princeton released SWE-bench: 2,294 real GitHub issues from 12 popular Python projects. Each task is graded by the tests from the pull request that fixed the issue: tests that failed before the fix must pass, and tests that passed must keep passing. The best model then, Claude 2, solved 1.96%. In August 2024, OpenAI had 93 software developers check 1,699 of the tasks for vague issues and unfair tests, and kept 500 clean ones as SWE-bench Verified, which became the coding score most labs reported. In February 2026, OpenAI said it would stop reporting it. Engineers reviewed 138 tasks that models kept failing and found at least 59.4% had tests that rejected correct fixes. And models from three labs could reproduce the exact fix from memory given only the task ID and a hint, because the projects were in their training data.

Facts checked: November 2026 (Jimenez et al., ICLR 2024; OpenAI, August 2024 and February 2026; Zheng et al., 2023; Anthropic, "A statistical approach to model evaluations", 2024; SWE-bench issue #465).

Remember

  • An eval is fixed tasks plus a fixed way to grade. Run each setup on every task several times.
  • Grade with tests where you can; a model grader has biases (order, length, its own style), so keep its questions narrow.
  • Small sets only show big changes. Compare task by task, keep some tasks hidden, and add new ones so the eval doesn't wear out.
