Why long sessions get worse

Read first: An agent is a while loop, Prompt caching

An agent's context only grows: every file it reads, every log and every failed attempt stays there until something removes it. Models use long contexts less reliably than short ones, so a long session gets slower, more expensive and sloppier. Knowing how harnesses shrink the context, and what that costs, tells you when to start fresh.

The idea

Picture your desk on a long debugging day. Every printout stays on it: logs, stack traces, three versions of the same config. In the morning your lead said "don't touch the payments schema". By evening that note is under a pile. You didn't forget it, but it is hard to find among everything else, and you start mixing up the old config with the new one.

An agent session works the same way:

  1. Everything stays. As you saw in An agent is a while loop, each step appends the tool result to the history and sends it all again. A file read at minute 10 and edited four times since is still in there, in its old version.
  2. Long context is used less well. Researchers keep measuring the same thing: as the input grows, models find and use the facts in it less reliably, even on simple tasks. Anthropic's own docs say "response quality degrades as a conversation grows", and its engineers call this context rot. The exact causes are still being studied, but the effect is real.
  3. The harness makes room. Near the limit, it removes old tool results, or replaces old turns with a summary. That is called compaction.
  4. Every summary loses something. Exact wording, early instructions, and why an approach was dropped can all disappear.
  5. Or you start fresh on purpose, with a short written brief. Often this is the best option.

Up close

Harnesses have three ways to shrink the context. Each one throws away something different:

MethodWhat is lost
Clear old tool resultsThe raw output of old tool calls. A short placeholder says it was removed, and the agent can run the tool again.
CompactThe old turns, replaced by a summary the model writes. Details the summary skipped are gone.
Fresh sessionThe whole conversation. Only files on disk remain: code, context files, your notes.

Anthropic's API offers the first two as request options, so you don't write the summariser yourself. Here is compaction (in beta, November 2026) on a request in the agent loop:

resp = client.beta.messages.create(
    betas=["compact-2026-01-12"],
    model=MODEL,
    max_tokens=16000,
    messages=msgs,
    context_management={"edits": [{
        "type": "compact_20260112",
        # summarise once the prompt
        # passes 150,000 tokens
        "trigger": {
            "type": "input_tokens",
            "value": 150000,
        },
        # replaces the default prompt,
        # so list all that must stay
        "instructions": (
            "Keep file paths, test"
            " commands, decisions"
            " and open bugs."),
    }]},
)
# a compaction block comes first;
# the API ignores what came before
msgs.append({"role": "assistant",
             "content": resp.content})

Two costs to remember. Summarising is itself a big request: the model reads the whole conversation to write it. And any shrink rewrites older parts of the history, so the prompt cache misses from that point on and has to build up again. That is why harnesses compact rarely and all at once.

Coding agents do this for you. Claude Code compacts automatically as the window fills. You can run /compact with a focus ("/compact keep the API changes") or /clear to start over. With 1-million-token windows, running out is now rare. The reason to clear is quality and cost: a focused context gives better answers and costs less on every step.

A fresh session needs a brief: a few lines that give the agent what the long session "knew", without the noise.

Goal: GBP refunds round wrong.
Code: services/refunds/
Note: amounts are in pence,
  see money.py
Don't: change the payments
  schema or gen/ clients
Done when: make test-refunds
  passes, with a new test
  for a half-penny case

Worked example

A two-hour Claude Code session compacts. Here is what its docs say comes back:

BeforeAfter compaction
Project CLAUDE.mdRead again from disk, in full
A rule you typed in chat at minute 5Only if the summary kept it
Your requests, key codeKept in the summary
Files read or editedUp to five, most recent first, read again
Old test runs and logsSummarised away

So anything that must survive belongs in a file, not in the chat. More on that in Agent memory is just files.

Your turn

Question 1 · ~2 min

At the start of a session you told the agent "never edit the generated clients in gen/". Two hours later it edits gen/orders_client.py. What most likely happened, and what is the fix?

Show answer

The rule was summarised away or buried. It lived only in the conversation. Either a compaction dropped it, or it sat deep in a long context full of other text. Put rules that must last in the project's context file, which is read again from disk after compaction. Better still, make it a check the agent can't skip, such as a permission rule that blocks writes to gen/ (see Hooks and permissions).

Question 2 · ~2 min

You've just fixed a refund bug. Next you want to add a metrics endpoint to a different service. /clear or /compact?

Show answer

/clear. Nothing from the refund work helps the new task. A compact would keep a summary of it, which you'd pay for on every step and which could distract the agent. It would also cost a big summarising request. Compact when you want to continue the same task with a lighter history. Clear when the task changes.

Question 3 · ~2 min

You've corrected the agent twice on the same thing ("use the existing retry helper"), and it still gets it wrong. Should you type a third, firmer correction?

Show answer

No: clear and write a better prompt. Both failed attempts are still in the context, and the model re-reads them on every step. A third correction just adds more of the same. Start fresh with one prompt that includes what you learned: "Use retry.with_backoff from lib/http, not a hand-written loop." Claude Code's own best-practice docs give the same advice.

Question 4 · ~3 min

A colleague says: "Starting fresh is a waste. My two-hour session already knows the whole codebase." Why does a fresh session with a ten-line brief often do better?

Show answer

The long session also "knows" a lot of wrong things. It holds old versions of edited files, dead-end attempts and huge logs, and models use long, noisy context less reliably. In a 2025 study by Chroma, every model tested answered questions better from a focused prompt of about 300 tokens than from the full 113,000-token history that contained the same facts. A brief keeps the useful part and drops the noise. The agent can re-read any file it needs in seconds.

Question 5 · ~3 min

Stretch: your harness clears old tool results once the context passes 100,000 tokens. Later, the agent re-runs a query against the staging database that it ran an hour ago. Is that a bug?

Hint
What did the agent see where the old result used to be?
Show answer

No, that's the design. The old result was replaced by a placeholder, so the agent ran the tool again to get it back. That is usually cheaper than carrying the old output on every step. It only hurts when the result can't be reproduced, like a one-off production query or data that has changed since. Ask the agent to write findings like that to a notes file, so they live on disk instead of in the context.

Use it at work

  • One task per session. When the task changes, run /clear (or your agent's "new session").
  • Start each session with a short brief: goal, where the code is, what not to touch, and how "done" is checked.
  • Move rules out of the chat into the context file, or into checks. If you need to pause a long task, ask the agent to write its progress to a file, then start fresh from that file.
  • After two failed corrections, stop correcting. Clear, and write one better prompt.

If someone asks "why does the agent get worse in long sessions?": "Everything it has read stays in its context, and models use long contexts less reliably than short ones. When it fills up, the harness summarises it and details get lost, so I keep one task per session and start each with a short written brief."

Interesting fact: Lost in the middle

In July 2023, Nelson Liu and colleagues from Stanford, UC Berkeley and Samaya AI gave models a question plus 20 Wikipedia passages, about 4,000 tokens, where only one passage held the answer. Then they moved that passage around. Accuracy formed a U shape: best when the answer was at the very start or end, worst in the middle. For GPT-3.5-Turbo, with the answer in the middle of 20 or 30 passages, accuracy fell below its score with no passages at all (56.1%). Versions of the models with longer context windows were no better at using what they were given. Models have changed a lot since then, but a 2025 study by Chroma of 18 models, including GPT-4.1, Claude 4 and Gemini 2.5, still found accuracy dropping as inputs grew longer, even on simple tasks.

Facts checked: November 2026 (Claude Code docs: context window, best practices; Anthropic API docs: compaction, context editing; Anthropic engineering blog, September 2025; Liu et al., 2023; Chroma, 2025).

Remember

  • Everything an agent reads stays in its context until removed, and models use long contexts less reliably than short ones.
  • Harnesses make room by clearing old tool results or compacting into a summary. Both lose details, and compaction is itself a big request.
  • One task per session, a short brief at the start, and lasting rules in files or checks, not in the chat.
